# 最小测试先行

## 要怎么做

每验证一个模块或接口，先做最小测试；所有子路径都绿了，才跑整份数据或全量流程。别一上来就全量。

按档推进，上一档不绿不进下一档：

1. 静态检查（零成本）：语法检查，比如 Python 用 py_compile，前端的 ES 模块也先过一道语法检查。
2. 纯逻辑单测（零网络）：用合成的输入验证分支、幂等、边界、异常兜底。
3. 单点接口最小测试（一次调用）：外部依赖先打一条，比如探维度、embed 一句、upsert 一行、用坏参数 curl 一次看降级。先证明通路、接口约定和降级都没问题，再谈规模。
4. 单模块小样（不超过一个批次）：跑 3～5 条，核对字段、缓存、幂等；跑第二次应该命中缓存。
5. 全绿之后，唯一一次全量：清掉标记，跑整份数据，尽量复用缓存（比如只补向量，不重新生成摘要）。

另外：

- 结合已知的坑，覆盖失败和降级路径，别只测正常路径（happy path）。
- 外部依赖要能降级、不阻断，下一轮能自己恢复。
- 全量要有上限护栏。

## 为什么

这是我明确要求的开发测试纪律。全量跑（全量的大模型调用、抓取、重建）慢且费钱；中途某个模块有坑，前面花掉的 token 全白费，还要重来。最小测试是不对称的投资：一次调用、一条合成数据、一段纯逻辑就能证伪的，绝不用整份数据去证。

依据类型：本人要求。

## 什么时候适用，什么时候不适用

- 适用：验证任何模块或接口，尤其是全量要做大模型调用、抓取、重建这类又慢又贵的流程。

## 例子

- 不合格：改完一个模块，直接对整份数据跑全量，跑到一半发现某个接口参数写错，前面的调用全白花。
- 合格：先过语法检查和纯逻辑单测，再对外部接口打一条请求，再跑 3～5 条小样核对字段和缓存，都绿了才跑那一次全量。
