# auto-task：按任务单全自动跑完开发、审查、走查

## 是什么

给一个 JIRA 任务单号，或一张列着一批单号的表格，主会话只当编排器、不写业务代码：取单 → 写开发清单、测试清单和设计草稿 → 派开发子代理改码 → 派审查子代理 → 编进本机开发环境 → 派走查子代理在浏览器里联调 → 汇总。每个单子一个目录，产物全部落盘。项目里有三个开发入口，它是「有任务单、全自动」的那一个。

## 为什么做它

- **目标是批量、无人值守、事后可查。** 说明文件写的目标就是把一个或一批任务单自动跑完，每个阶段的报告都落盘，供事后复盘。
- **任务单本身信息不全。** 需求正文经常是空的，细节在标题、评论和附件里。只读正文就开工，等于没读需求。
- **一个人逐步转交太累。** 取单、拆清单、改码、审查、走查，每一步都要有人把上一步的产物交给下一步，主会话的上下文也会被这些过程挤满（推测，材料里没有直接写这条动机）。

## 设计思路

1. **一条生命周期，三个入口。** 它不是一条独立流水线，而是项目统一开发流程（需求 → 设计 → 开发 → 审查 → 构建 → 走查）的一种入口配置。它和另外两个编排器（单个需求的半自动入口、修缺陷的入口）共用阶段名、状态词和审查出口标准，区别只在门禁多少：它没有人工门禁。
2. **编排者只派活、只记账**（编排者-执行者模式，orchestrator-worker）。改码、审查、走查都交给子代理；主会话只负责写清单和设计、派活、写状态、读报告、写汇总。
3. **能隔离就并行，争用点串行**（扇出-汇聚，fan-out/fan-in）。多个单子各用一份物理隔离的工作副本，开发和审查可以同时跑；走查共用同一个开发库和同一个管理员账号，而且会写库，所以强制逐个跑。
4. **状态只有一个写入口**（单一数据源，single source of truth）。状态文件只能经脚本命令写，脚本拒绝不在白名单里的状态值；总索引从各单的状态文件重建，不手写。
5. **不能阻断，也不许沉默。** 全自动链路一趟走完，不做「审查 → 修复 → 再审」的回环；但审查查出阻断级问题时，必须在状态和汇总里显眼标出来。
6. **子代理不自己找范围。** 派活时把上下文包写全：单号、工作副本的绝对路径、输入输出文件、这一轮只做哪一组、红线，以及「启动先读项目已知坑、再核对表结构」。子代理不继承主会话的记忆，不写全它就会自己猜。

## 实现思路

组成：

- 说明文件 128 行：按「解析入参 → 取数和生成清单 → 每单流水线 → 汇总」四段写的操作手册。
- 任务工具脚本 699 行，只用标准库加一个表格解析库：取单（连评论和附件清单）、从表格里抽单号并去重、置备工作副本、写状态、重建索引、校验主副本有没有被误改、纯页面改动的临时同步和回滚。
- 调用时自动把当前任务索引注入给模型（上下文注入，context injection）。
- 配合三个项目级子代理（开发、审查、走查），和两个 skill：[dev-rebuild](dev-rebuild.md) 当构建门，[chrome-walkthrough-flow](chrome-walkthrough-flow.md) 给走查子代理当方法。
- 一份项目已知坑清单，子代理启动时先读。

一次运行的顺序：

1. 解析入参，得到单号清单，先给我看一眼。
2. 每单：取数；主会话亲自写开发清单（按独立的需求组分节）、测试清单和设计文档草稿；状态置为「清单就绪」。
3. 置备：只有一个单子时直接在主工作副本上改；多个单子时每单复制一份工作副本，并存一份主副本的状态快照。
4. 开发：独立需求组超过 2 个就按组拆，一组派一个开发子代理，同一副本里的几组串行做。
5. 审查：审查子代理只读，报告第一行写阻断数，由主会话落盘。
6. 构建门（只在单个单子时有）：改了后端代码就调 dev-rebuild，先预演一遍看有没有别人未完成的改动；编译失败就把报错交回同一个开发子代理续聊修，最多 2 次。
7. 走查：所有单子都开发、审查完以后逐个走查。默认跑写路径联调，只碰本次自建的测试单据；带开关时只读。
8. 收尾：按开发报告定稿设计文档；多副本模式下校验主副本没被误改；重建索引；给我一段中文汇总。

分工：取数、副本、状态、索引、隔离校验交给脚本；读单子拆清单、写设计、派活、读报告留给模型。

## 关键决策

| 决策点 | 选了什么 | 没选什么 | 为什么 | 依据类型 |
|---|---|---|---|---|
| 并行靠什么 | 主会话后台派子代理，每单一份复制出来的工作副本 | 代理团队（agent teams）；版本库自带的工作树隔离 | 版本控制用的是 SVN，没有工作树隔离；代理团队当时还是实验特性 | 设计文档（2026-10，列为不做）；流程规范 |
| 副本怎么来 | 复制整个主工作副本，再在副本里还原到干净基线 | 从服务器全新检出（保留成可选参数） | 复制只要 2～5 秒，检出慢 | 实现代码 |
| 单个单子要不要副本 | 不建，直接在主工作副本上改 | 一律建副本 | 副本是为多单并行写隔离设的，单个单子没有冲突；直接改主副本还能编进本机开发环境验新功能 | 本人要求（2026-08-10） |
| 走查并不并行 | 严格逐个跑 | 和开发、审查一样并行 | 开发环境共享，同一个管理员账号切角色，而且走查会写库，并发会互相写坏 | 技能说明文件；流程规范 |
| 并发上限 | 同时最多 3 条流水线，可调 | 不设上限 | 限制用量和对开发环境的争用；为什么是 3，材料里没写 | 技能说明文件；推测（为什么是 3） |
| 审查出了阻断级问题 | 不回退，但必须写进状态和汇总并显眼标出 | 静默继续；像另两个入口那样阻断回退 | 全自动入口没人在场拍板，但结果不能悄悄带病往下走 | 流程规范 |
| 要不要回环 | 一趟走完；唯一的修复环是编译失败，最多 2 次 | 改到通过为止 | 项目定过循环的规矩：要有上限，超限交给人 | 流程规范（2026-10-28） |
| 状态怎么写 | 只经脚本命令写，非法状态值直接拒绝；索引从状态文件重建 | 主会话或子代理手改状态文件、手写索引 | 一处一源，派生物只从真源重建 | 实现代码；流程规范 |
| 大单子怎么派 | 独立需求组超过 2 个，一组派一个开发子代理 | 一个子代理全包 | 第一次实跑时，一个子代理接了 5 组只做完 1 组 | 技能说明文件 |
| 新功能在开发环境里能不能验 | 单个单子审查后加一道构建门，调 dev-rebuild 编进去 | 标「待部署」交给人 | 原先照「本机不能编译」的旧说法，新功能一律验不了；那一轮优化把这项列为杠杆最高 | 设计文档（2026-10）；迭代记录（2026-10-28） |
| 构建门撞上别人的半成品 | 先预演看未提交改动清单，不属于本单的先问我 | 直接编 | 2026-10-22 出过把别的会话的半成品编进去、全站报错的事 | 设计文档（2026-10 风险表）；事故复盘（2026-10-22） |
| 测试清单已存在时 | 只补缺、加标注，不覆盖 | 每次重新生成 | 需求分析阶段产出的测试清单是准绳，两份并存会打架 | 流程规范 |

「依据类型」只说明这条决策是凭什么定的。对应的原始材料不随本库提供，读这张卡不需要去找它们。

## 怎么用

- 我会说：「跑一下这个任务单」「把这个表格里的单子都过一遍」。参数是单号，或表格路径加可选的列名；另有一个开关让走查只读。
- 前提：JIRA 账号放在不进版本库的本地配置里。
- 产出：每单一个目录，放任务正文、开发清单、测试清单、设计文档、开发报告、审查报告、走查报告和截图、状态文件；外加一份总索引和一段汇总（终态、阻断数、报告位置、要产品确认的业务语义、提交前要人工看差异）。
- 不用它：没有任务单的单个需求，交给半自动入口（有两道人工门禁）；修缺陷，交给缺陷闭环入口；日常小改动，直接用计划模式加主会话改。

## 好处

| 同一件事 | 没有它 | 有了它 | 依据 |
|---|---|---|---|
| 一个任务单从取数到走查 | 主会话逐步做、逐步转交 | 一条命令跑完，每步报告落在单子目录里 | 实测。真实运行：本项目 3 个单子，2 个走到「完成」，1 个停在「已审查」等走查（2026-07～08） |
| 读需求 | 只看正文，而正文常是空的 | 评论和附件清单一起抓下来 | 设计意图，未实测 |
| 多个单子同时改 | 改动混在同一份差异里 | 各自副本，差异天然隔离；收尾校验主副本没被误改 | 设计意图，未实测 |
| 审查查出阻断级问题 | 可能悄悄沉淀 | 状态和汇总里显眼标出 | 设计意图，未实测 |
| 单个单子的新功能 | 只能标「待部署」 | 构建门编进本机开发环境，走查直接验 | 设计意图，未实测。构建门 2026-10-28 才加上，之后本项目没有新单子走过它 |
| 换个项目 | 从头搭 | 已移植到另外两个项目，近 400 天的 3 次调用都来自移植版 | 实测。使用统计（2026-11-23） |

## 代价与局限

- **在本项目里基本没被用起来。** 方法论审计时它只跑过 1 次，而且收尾带病：走查子代理中途中断、改动没部署、新功能验不了。2026-11-23 复评时，近 18 天改代码的会话调用它 0 次，实际干法是「计划模式 → 主会话直接改 → dev-rebuild → 浏览器自验 → 派审查子代理 → 人工确认提交」。复评的建议是它只留给批量任务单。同样的现象见[能力装得多用得少，瓶颈在采纳](../50-经验教训/能力装得多用得少瓶颈在采纳.md)。
- **没有门禁，就要有人看结果。** 带阻断级问题的结果靠人事后读索引，没人看就沉淀下来。
- **一趟走完不回环。** 审查查出的问题要人接手修。
- **多单模式验不了新功能。** 复制出来的副本不是运行中的实例，只能标「待部署」。
- **子代理多，用量大。** 它天生要扇出，和[默认不派子代理铺开](../10-协作规矩/默认不派子代理铺开.md)那条规矩有张力：真跑批量之前，先按那条规矩说清要派几个、估多少用量。
- **状态值没有单一可执行来源。** 脚本里有一份状态白名单，另两个入口各自在说明里内联一份，都声称以流程规范为准。
- 子代理定义改了要重开会话才生效，见[项目级子代理什么时候加载](../40-技巧/项目级子代理什么时候加载.md)。

## 踩过的坑

1. **一个子代理吃不下大单子。** 5 个需求组只做完 1 组。之后按组拆，一组一个子代理。
2. **范围中途变了没地方放。** 第一次实跑中途把范围收窄到一个模块，另一侧已改的代码回退重做。状态机原本有个悬空的「范围重定」态，后来才正式定义成「范围回退、重拆清单」。
3. **旧说法在多处复述，改一处漏一处。** 「本机不能编译、新功能验不了」同时写在它的说明文件、开发子代理的定义和会话启动时的提示里；同一组硬约束在 5 个编排器和子代理的文件里各抄一份。2026-10-28 收口时查出 5 组跨文件不一致，改成一行指向常驻规则文件。2026-11-23 写卡时，任务区自带的一份配套说明里仍留着旧说法。
4. **结果长期悬着。** 第一次实跑的结论写着「需产品确认、需部署验证」，之后没人回头处理。
5. **构建门会把别人的半成品一起编进去。** dev-rebuild 编的是工作副本里所有未提交的改动，所以构建门第一步是预演、看清单，撞上了先问。

## 换个项目怎么复用

可以照搬的做法：

- 编排者-执行者（orchestrator-worker）：主会话只派活和记账，清单和汇总由它写。
- 扇出-汇聚（fan-out/fan-in）加并发上限；共用同一环境的步骤强制串行。
- 每个任务一份物理隔离的工作目录；置备时给主目录拍快照，收尾比对它有没有被误改。
- 单一数据源（single source of truth）：状态只有一个写入口，状态值用白名单；索引从状态文件重建。
- 上下文包：子代理的输入输出、范围、红线都在派活时写明，不让它自己找。
- 不能阻断就显式标注；单个任务失败只跳过它，不中断整批（故障隔离）。
- 唯一的修复环写死上限，见[循环要有界、有门禁、过程落盘](../50-经验教训/循环要有界、有门禁、过程落盘.md)。

要按项目重写的：任务来源和认证方式、副本的置备方式（用 git 的项目直接用工作树）、构建门命令、走查的账号和环境、项目已知坑清单、落盘目录。另外两个项目照此移植时，一个带了脚本，一个只留了说明文件。
