# agent-craft：写规则、写 skill、派子 agent 之前先翻的行动卡

## 是什么

7 张「行动卡」，每张四段：触发、建议、代价、出处。我（或 agent）往常驻规则文件里加规则、写 skill 的描述和调用方式、跨 skill 调用、派并行子 agent、把流程某一步挪到别的阶段、准备宣布完成时，它把最相关的 1～3 张拿出来。只给提示和代价，我拍板。目录里还放了两件工具：技能库的确定性检查脚本，和按调用去重的用量统计脚本。

## 为什么做它

- **判断点反复出现。** 写 skill、改规则、编排子 agent 时，总要判断「这条规则写成文字还是做成检查」「这个 skill 该不该让模型自动调用」「派几个子 agent」。材料里只写了它要在这些时刻用上，没写做它之前具体哪里疼；「之前每次临场凭感觉」是推测。
- **别人的经验散在提交记录里。** 公开 skill 仓库的作者踩过同样的坑，决策和反悔都留在源码、决策文档和几百个提交里；不整理成卡，用的时候想不起来，也不知道去哪找。
- **只抄做法会把习惯当银弹。** 光记「该怎么做」、不记「代价和什么时候不该这么做」，照搬到不合适的场景就出错。

## 设计思路

1. **卡片四段，代价必填。** 没有「代价 / 什么时候不该这么做」的卡不合格。
2. **命中才提示，一次 1～3 张，我拍板。** 卡是启发式，不是硬规则；和我已定的约束冲突时以我为准。
3. **每条建议能回查。** 出处写到作者仓库的文件、行号和提交版本；卡里说的是那个仓库的事实，本机已有对应实例的单独点名。
4. **冲突并列，不替我裁决。** 例如描述该「多列同义触发词」还是「每个分支一个触发词」，两种说法并列，各标代价。
5. **能用命令判定的规则做成检查**（确定性检查，deterministic check）。这是卡 1 的主张，它自己也照做：配了一个只读的技能库检查脚本。
6. **不追上游。** 作者仓库更新后，只有结论被推翻才改卡；连续几轮复盘都没触发的卡删掉。

## 实现思路

组成：

- 说明文件 132 行：给模型的元指令；7 张卡（加规则前先问四句、靠判断判停的循环只跑一轮、见过它红才算证据、挪出流程要指明谁来执行、worktree 并行的坑、跨 skill 调用、描述与调用方式）；出处索引和本机实例；维护约定。
- 两份写作参考：作者写作指南的中文译本，开头标明「是参考，不是流程」。
- 技能库检查脚本 282 行，8 类检查：文件头可解析且名字和目录一致、描述长度预算、项目前缀、来源说明、调用了只能手动运行的 skill、引用了不存在的 skill、文档和实际不一致、同名遮蔽；另报各作用域常驻描述的总字数。

## 怎么用

- 我会说：「写一条全局规则：以后……」「该派 subagent 还是用 agent team」「这个 skill 的描述怎么写」。改技能库的计划里，规定每一步改说明文件、子代理、记忆之前先调它拿判断卡。
- 输出：最相关的 1～3 张卡，每张带建议、代价、出处，由我拍板。两件工具可以直接跑：改完技能库跑检查脚本；量 skill 用了几次跑用量脚本。
- 不用它：创建 skill、打包、跑触发率评测（交给 skill-creator）；把循环落地成有界计数、超限停下问人（交给循环工程的 skill）；软件设计和表结构取舍（交给设计原则、表结构设计的 skill）。

## 代价与局限

- **卡片本身帮上多少忙，没有数据。** 蒸馏时计划「挑 2～3 个真实任务回测」，至今没做，回测表是空的。
- **卡里是别人仓库的事实。** 本机已有对应实例的要另外点名，否则读者会把作者的情况当成本机的。
- **冲突裁决还是要跑评测。** 卡 7 两种说法并列，拿不准时得跑触发评测来定，一次簇评测改前改后要跑 3 轮。
- **只覆盖一位作者。** 补新作者的卡要再蒸馏，而蒸馏工具（一个自建 skill）2026-11-04 已退役，用之前得先从备份恢复。
- **检查脚本只管能用规则判定的问题**（解析、长度、登记、引用）。规则内容对不对、几处说法有没有打架，它查不出来。

## 踩过的坑

1. **自带触发评测在已装同名 skill 时失真。** 10 条全 0：临时副本和已安装的正式版同名竞争，评测又只看第一个工具调用，20 个会话 60 秒就全结束了。改为在真实安装状态下用无头模式探测。
2. **作者日期和合入日期不一样。** 独立审核指出 3 处日期错，用版本库复核才发现是变基（rebase）让两个日期分开了。此后规定引用作者日期。
3. **证据写法不统一。** 证据常写成「一个文件、多个行号用逗号隔开」，回查脚本一开始不认，补了这种写法。
4. **盲测评分方也会判错。** 它判某条建议「没有出处」，其实提交说明原文就写了；评分结果不能当终审，要回原文复核。
5. **描述里的引号。** 双引号里再嵌双引号，文件头提前截断，子代理静默不加载（见好处表里链接的那条经验教训）。检查脚本的第一类检查就是为它。

## 换个项目怎么复用

可以照搬的做法：

- 行动卡格式：触发、建议、代价、出处四段，代价必填；命中才提示，一次 1～3 张。
- 从公开仓库蒸馏经验的流水线：盘点 → 作者画像 → 并行提取候选 → 脚本回查证据 → 独立审核定档 → 人拍板晋级。
- 保真盲测：答题方只读卡，评分方只读原文，最后人工回原文复核。
- 冲突的说法并列，标各自代价，不替人裁决。
- 确定性检查（deterministic check）：能用命令判定的规则写成检查脚本，不写成文字。
- 技能库检查清单：文件头可解析、描述长度预算、调用了只能手动运行的 skill、引用不存在的 skill、文档与实际一致、同名遮蔽。
- 用量按调用去重后再下结论。

要按项目重写的：本机实例一栏、检查脚本的扫描范围和白名单、描述长度预算、要蒸馏的作者和仓库。
