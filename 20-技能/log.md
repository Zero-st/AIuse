# log：开发环境报错，先从日志里找到这一次

## 是什么

页面报错、点按钮后端返回 error 时，让 agent 按固定步骤翻服务日志：定位日志文件 → 看近况 → 按关键字过滤 → 找最内层的根因 → 必要时回退到另一份日志。最后交一份简报：查了哪份日志、命中的原文行、一句话根因、出错的类或 SQL 映射、修复方向。它是报错时第一个出场的，只诊断，不修。

## 为什么做它

- **每次都从头 grep。** 日志在哪、哪份文件才有完整的异常栈、该用什么关键字，agent 每次重新摸，主对话里直接 grep 一通。
- **一个错误前提害它漏报。** 早期版本假设「异常栈在按日滚动的日志里」。2026-08-11 实测：按日日志里业务包的栈帧是 0 处，完整栈全在 Tomcat 的控制台输出文件里（上千处）。照旧做法，按日日志没看到异常就会报「没报错」。
- **报错类的说法太多，几个 skill 互相抢。** 2026-11-03 扫会话记录，我的真实说法都是「地址 + 报错 / 很慢 + 排查 / 解决」。排障相关的 5 个 skill 在 60 天里几乎没自动触发过；「500、报错、异常、定位」这些词同时写在 3 个描述里。

## 设计思路

1. **只读，用工具白名单兜底。** 说明文件只允许 tail、grep、ls、sed、head、wc 这类只读命令和读文件，模型想改也改不了。
2. **先看小的，再回退到全的。** 先查当天的按日日志，小、快；没有业务异常就必须回退到控制台输出文件，不能凭按日日志「干净」就下结论。
3. **找「最近一次」看行号，不看文件尾。** 控制台输出文件是追加写的，跨重启、不按日滚动，文件尾可能只是普通的 SQL 打印。要 grep 全文，取行号最大的命中，再打印那一段。
4. **用高信号锚点，不用裸的 ERROR。** 裸的 ERROR、Exception 会被两类噪声顶到前面：SQL 列名里带 error 的字段，每次重启时日志框架的启动报错。改用全局异常拦截器打的那一行（带用户、来源页、类、方法、请求地址和参数）、「Caused by」、数据库错误码、业务包栈帧。
5. **按动词分流**（用户拍板）。「排查」归它，「修掉」归缺陷修复的 skill，「解决」类小改动主对话直接做；慢、卡、超时全归性能诊断。异常栈已经在手、要深挖源码和库的，交给异常深挖的 agent。

## 实现思路

- 组成：一份说明文件 79 行，没有脚本。调用时自动注入两样东西：最新的按日日志文件名，控制台输出文件里最近 5 条高信号锚点（带行号）。模型一开口就有现场。
- 一次运行：四步排查加第五步回退，然后按四种情况分支：
  - 命中异常：读最内层的 Caused by，定位到类或 SQL 映射，给修复方向；
  - 按日日志没异常：强制回退；
  - 日志文件不存在：说明服务没起，先查状态，要起服务交给编译重启的 skill，不自己手写启动命令；
  - 文件为空：回退，或看前一天。
- 时好时坏、抓不到稳定证据的，转去读缺陷修复 skill 里「先造一条稳定变红的回路」那份参考，仍然只诊断。
- 分工：找文件、过滤、打印交给命令；判断哪条是根因、出错在哪一层、修复方向，留给模型。

## 关键决策

| 决策点 | 选了什么 | 没选什么 | 为什么 | 依据类型 |
|---|---|---|---|---|
| 权威日志 | 控制台输出文件是权威源，按日日志只当快速入口 | 只看按日日志 | 按日日志常缺业务栈帧，实测 0 处对上千处 | 事故复盘（2026-08-11） |

| 过滤关键字 | 高信号锚点：异常拦截器那行、Caused by、数据库错误码、业务包栈帧 | 裸的 ERROR、Exception | 裸词被 SQL 列名和启动噪声顶到前面，会误报 | 事故复盘（2026-08-11） |

| 报错类请求怎么分 | 排查 → 它；修 → 缺陷修复；「解决」→ 主对话；慢 → 性能诊断；「500」这个词只留在它的描述里 | 几个 skill 都写上报错类关键词 | 撞车的词让谁都叫不到；缺陷修复全闭环太重，小修不该走它 | 本人要求（2026-11-03）；评测记录（簇评测 11/16 → 15/16） |
| 服务没起来怎么办 | 先查状态，交给编译重启的 skill | 自己手写构建和启动命令；照旧写「本机不启服务」 | 旧说法在有了编译重启 skill 之后过时了 | 迭代记录（2026-11-03） |

## 怎么用

- 我会说：「这个页面报 500，排查一下」「点审核后端返回 error，什么原因」「看下后端日志有没有报错」。可以带关键字或日期。
- 输出：一份简报，命中的原文行带文件和行号；异常时间以行内时间戳为准，可能是几天前，如实标。
- 不用它：要修（交给缺陷修复的 skill）；慢、卡（交给性能诊断）；已经拿着异常栈要追到源码和 SQL（交给异常深挖 agent）。

## 代价与局限

- **用得少。** 近 400 天 3 次，本项目 2 次都是我手动敲的命令。报错时主对话常常直接 grep，没叫它。
- **环境事实写死在说明文件里。** 日志目录、文件分工、日志级别配置都是这一个开发环境的；换环境要整段重写。
- **只看日志。** 日志里没留下痕迹的问题（前端脚本错误、数据不对但没抛异常）它查不到。
- **「没有异常时如实报告」这条行为没测过。** 评测集里有这条用例，一直没跑。

## 踩过的坑

1. **按日日志「干净」不等于没报错。** 业务异常栈走的是控制台输出，不进按日日志。
2. **最近一次报错不在文件尾。** 文件尾常是普通 SQL 打印，要按行号取最大的命中。
3. **裸的 ERROR 会误报。** SQL 里带 error 的列名、每次重启时日志框架自己的报错，都会被当成异常。
4. **和深挖 agent 抢活。** 触发评测里「跨好几个类、帮我深挖到哪个 SQL」本该交给深挖 agent，却两次都叫到了它。2026-11-03 排障簇调整时，两边的描述各留各的词：「500」只在它这里，「异常栈」只在深挖 agent 那里。

## 换个项目怎么复用

可以照搬的做法：

- 工具白名单（allowed tools）实现只读，而不是只靠文字约束。
- 上下文注入（context injection）：调用时把最新日志文件名和最近几条锚点直接摆给模型。
- 先查小的快速入口，查不到必须回退到权威源，不凭「没看到」下结论。
- 追加写的日志按行号找最近一次，不看文件尾。
- 高信号锚点代替裸关键字，先列出本项目的已知噪声。
- 报错类请求按动词分流（排查、修、解决、慢各归一处），一个触发词只留给一个 skill。
- 固定的简报格式：查了哪份、原文行、根因、位置、方向。

要按项目重写的：日志位置和各文件的分工、日志级别配置、高信号锚点、服务没起来时交给谁。
