# db-to-dbscript：开发库改完，补一份能随发版走的数据库脚本

## 是什么

在开发库上建了表、改了字典或配置、订正了存量数据之后，把「这一次改动的最终结果」写成发版脚本：按语句类型放进五个子目录之一（表结构、包和过程、视图、初始化数据、其他和订正），自动加头注释和执行器指令、剥掉提交语句、检查编码和文件名。它在「开发库已经改好」和「交给人随发版执行」之间出场。配套一个收尾钩子：会话结束时，如果这次改过开发库却没有对应的脚本，拦一下提醒。

## 为什么做它

- **改动只在开发库生效。** 这个系统的数据库改动，只有写进发版脚本目录，才会随发版同步到测试和生产。平时图快，常用数据库 MCP 直接改开发库，改完只在开发库生效；忘了补脚本，测试和生产就没同步。
- **手工补容易漏格式。** 一次下拉框修复就踩了这个坑：先改好开发库，脚本是事后才补的。手工补还容易漏格式：少写首行的执行器指令、多写提交语句、没做成可重复执行。
- **发版目录每次清空，脚本可能重跑。** 不幂等，第二次执行就报错。
- **订正改错了不可逆。** 后来盘点发现，订正类脚本没有「备份 → 核验 → 回滚」的模板，手工写的范例却反复出现。

## 设计思路

1. **把已有约定固化进生成器，不发明新规则。** 子目录路由、首行执行器指令、不写提交、幂等，都是项目早就有的约定。
2. **收尾门禁，不逐条提醒。** 只在会话结束、且真有「写了库但没落脚本」的缺口时提醒一次。
3. **钩子只提醒，生成交给 skill 和人。** 取「最终净改动」要判断，钩子自动落盘会把中间态也写进去。
4. **门禁自己坏了不能拦人**（失败放行，fail-open）。钩子出错或拿不到证据就静默放行。
5. **订正必带四段。** 估算影响行数、建表备份、核验、回滚；回滚只写在头注释里。
6. **只登记，不提交。** 生成后提示加入版本库登记；什么时候在哪个库执行由我决定。

## 实现思路

组成：

- 说明文件 110 行：何时用、路由表、订正四段、文件规范、用法、流程、红线、7 项验证清单（完成定义，definition of done）。
- 生成脚本 205 行：按语句关键字路由（判不准就报错，要求手动指定目录）；剥掉独立的提交语句并告警；拼头注释（作用、影响行、幂等策略、字典参考、配套代码）；同名文件不覆盖，除非显式强制；给「把 SQL 当成列值存」的场景转义单引号。
- 两个钩子：写库前的守卫判定为写语句时，往一个留痕文件追加一行；收尾钩子按会话读留痕、查版本库里脚本目录有没有新增或修改、用指纹去重，三项都满足才拦。收尾钩子的通用做法见[用结束钩子做收尾门禁](../40-技巧/用结束钩子做收尾门禁.md)。
- 一条按路径触发的规则：碰到脚本目录时注入规范要点。

一次运行：确认这次改动的最终净结果 → 模型写成幂等、无提交的 SQL → 脚本路由并落盘 → 模型用只读查询复核语法和结果 → 提示登记，不提交。SQL 本身由模型写，脚本只管打包和格式。

## 怎么用

- 我会说：「写个发版脚本，给某个分类配上……」「刚才用 MCP 执行的那条改字典的更新，补个发版脚本」「写个数据订正脚本，带备份和回滚」。收尾钩子拦下时也走它。
- 输入：已在开发库验证过的 SQL，加文件名、标题、作用、影响、幂等策略。输出：落在对应子目录的一份脚本，并提示登记。
- 不用它：审核流程条种子（交给流程条的 skill）；规范化、合并已有种子（交给种子合并的 skill）；从零设计表结构（交给表结构设计的 skill，设计完再回来落盘）；直接在生产库手动执行的订正（交给生产订正的 skill，那种块不进发版目录）。

## 好处

| 同一件事 | 没有它 | 有了它 | 依据 |
|---|---|---|---|
| 说「写个数据订正脚本，带备份和回滚」 | 8 条簇评测里只有这条没叫到它，主对话直接跑命令 | 8 条全对，跑两轮都对 | 实测，评测记录（2026-11-03；8 条用例，改前 1 轮、改后 2 轮） |
| 改了开发库、忘补脚本 | 靠人记；有过事后才补的先例 | 收尾时自动拦一次，指向生成器 | 设计意图，未实测。没有统计过拦截次数 |
| 手写发版脚本的格式 | 漏首行指令、多写提交、编码和换行不对 | 生成器自动加指令、剥提交、检查编码和文件名 | 设计意图，未实测。没量过手写的漏项率 |
| 只查不改的会话 | — | 没写过库就静默放行，零打扰 | 设计意图，未实测 |
| 发版重跑 | 不幂等的脚本第二次执行报错 | 规范强制幂等：建索引捕获「已存在」、配置按主键整列重置、种子按键先删后插 | 设计意图，未实测 |

## 代价与局限

- **门禁只看有没有，不看对不对。** 收尾钩子只认「脚本目录里有新增或修改的脚本」，不核对内容是否对应这次改动；随便有一个脚本改动就放行。
- 留痕文件按会话过滤，但跨会话累积、不清理（体积很小）。
- 自动路由在「初始化数据」和「一次性订正」之间是启发式，判不准要手动指定。
- 发版那边清空目录用的是另一套目录名，和本机目录名不一致；发版侧出问题以构建主机为准。
- 只管打包，不保证 SQL 本身正确，正确性靠写 SQL 的人和只读复核。

## 踩过的坑

1. **数据库 MCP 的普通更新静默无效。** 不显式提交就不生效，所以在开发库执行时要用匿名块包住并提交；但落进发版脚本的版本必须把提交去掉。两处做法相反，最容易混。
2. **几处说法打架。** 本 skill 的示例用了系统临时目录，和全局「禁用系统临时目录」冲突；另一个 skill 的种子模板里还带着提交语句，和这里的「禁止提交」矛盾。一次跨文件一致性盘点（2026-10）时统一。
3. **编译缓存进了版本目录。** 生成脚本旁边的编译缓存被纳入版本管理，体系评估时才发现。
4. **中英文目录名。** 发版流水线按中文目录名清空，磁盘上和文档里是英文目录名；只能写英文、以构建主机为准。

## 换个项目怎么复用

可以照搬的做法：

- 把项目已有的约定固化进生成器：生成器负责格式，模型负责内容。
- 收尾门禁：只在有缺口时提醒一次，指纹去重；两个钩子之间用一个留痕文件解耦，不直接互相调用。
- 失败放行（fail-open）：门禁自己出错时放行，不卡人。
- 「已完成」从版本库状态现场算出来，不另存状态。
- 数据订正四段：估算、备份、核验、回滚；回滚只写在注释里，别让它进会被自动执行的目录。
- 脚本只登记不提交，执行时机交给人。
- 验证清单当完成定义（definition of done）。
- 触发评测（trigger eval）按簇做：相邻几个 skill 的正例和负例放在一组里测，看会不会叫错。

要按项目重写的：子目录和路由关键字、执行器指令、提交约定、幂等写法（取决于数据库）、版本库命令、写库守卫的读写分类。
