# bugfix：缺陷修复全闭环，回环有上限

## 是什么

我说「把这个 bug 修掉」「生产报错了，帮忙修复」时出场。主会话只当编排器，按阶段把活派出去：
- 分诊：缺异常栈就先叫日志首查；
- 定位：派异常深挖 agent；
- 复现：先用一条请求探针，打不到的再派走查 agent 只读复现；
- 门禁：确认根因和修复方案；
- 修复：派开发 agent 在独立副本里改；
- 重建：叫编译重启的 skill；
- 回归：先重跑探针，再走查；
- 审查：派审查 agent，阻断级问题为 0 才收尾。

它是项目统一开发流程的「缺陷入口」，和「单个需求」「按任务单批量」两个入口共用阶段名和状态。

## 为什么做它

- **主干上缺一个闭环。** 说明文件开头写的初衷：补齐「日志分析 → 定位 → 复现 → 修复 → 回归」这条主干上最大的闭环缺口。之前缺陷要么夹在需求开发里顺手修，要么主对话直接改，没有复现这一步，也没有「回归没过就回去重新定位」的回环。
- **回环原本没有上限。** 2026-07-24 盘点循环时发现，缺陷修复和需求开发两个编排流程，回退重做都没有计数。
- **「线上」只是写在描述里。** 2026-11-03 覆盖复评发现：描述里写了能处理生产报错，实际流程只会在开发环境跑，碰不到生产日志和生产库。

## 设计思路

1. **编排者只派活**（编排者-执行者模式，orchestrator-worker）。日志、定位、复现、修复、重建、审查都交给现成的 skill 和 agent；编排器只做分诊、串接、复述门禁，不把子逻辑抄进来。
2. **先复现，复现要安全。** 能用一条请求复现的，先在没修的构建上跑出红；打不到的才派浏览器走查，而且只读。必须有数据才能触发的，只用本次自建的测试单据。只读和自建都复现不了，就记「无法安全复现」，停下来问我。
3. **根因和修复方案过门禁再动手。** 把根因、打算改哪些地方、影响面、回归点复述给我，确认后才改。门禁是阻断式的。
4. **回归以修前那条红探针变绿为准。** 修前红的那条要变绿，其余探针不能回退；然后带上同模块已有的测试用例清单去走查，不每次临时拼用例。
5. **回环写死上限**（有界重试，超限交人）。回归没过就回去重新定位，最多 2 轮；审查有阻断级问题就回去修，也是最多 2 轮。第 3 次还不过就停下，把现象和试过的方案交给我。
6. **线上分支如实降级。** 生产报错时，证据靠我贴日志、截图、请求地址和时间；结论标「生产现象、开发环境推断」；修复附回退文件清单，涉及数据的附回滚脚本；收尾写「待生产部署验证」，不写「已修复」。

## 实现思路

- 组成：
  - 说明文件 68 行，按阶段写的编排手册；
  - 一份诊断纪律参考（改造自上游），讲先造一条能稳定变红的回路、再列 3～5 个可证伪的假设，不凭读代码下结论；
  - 一个人工介入回路的脚本模板，给只能靠人点页面才能复现的情况用。
- 配合：日志首查 skill、异常深挖 agent、走查 agent、开发 agent、编译重启 skill、审查 agent，加一个请求探针脚本。
- 状态：写进一份机器可读的状态文件，每过一个阶段更新一次，中断后可以续跑。字段定义只在流程规范里有一份，说明文件里只写指针。
- 第 2 轮修复优先续聊第 1 轮那个命名的开发 agent，保留它读过的上下文。

## 关键决策

| 决策点 | 选了什么 | 没选什么 | 为什么 | 依据类型 |
|---|---|---|---|---|
| 和需求开发分开 | 单独一个缺陷入口，带复现和回归回环，不做需求分析 | 缺陷都塞进需求开发里顺手修 | 缺陷的核心是复现和回归，需求开发里没有这两步 | 技能说明文件 |
| 回环上限 | 回归和审查各最多 2 轮，第 3 次停下问人 | 改到通过为止 | 循环要有界、超限交人；盘点时发现两个编排流程回退都没计数 | 评测记录（2026-07-24 盘点）；迭代记录（2026-10-28） |
| 复现手段 | 先用请求探针；打不到的才派浏览器，而且只读 | 一律派浏览器走查 | 探针可重复，回归时直接重跑；探针见红就不再派浏览器 | 流程规范 |
| 复现不了 | 记「无法安全复现」，停下问要不要给测试单据或账号 | 为了复现去改存量数据 | 共享环境上的存量数据改了回不去 | 流程规范；技能说明文件 |
| 生产报错 | 加线上分支：证据靠我贴，修复附回退清单和回滚脚本，收尾标「待生产部署验证」 | 描述里写能修生产、流程照旧只在开发环境跑 | 复评指出描述和能力对不上：做不到的要么补上，要么从描述里删掉 | 评测记录（2026-11-03 覆盖复评）；迭代记录（2026-11-03） |
| 回归基线 | 先找同模块已有的测试用例清单交给走查 | 每次临时拼用例 | 复评指出回归用例不沉淀 | 评测记录（2026-11-03 覆盖复评） |
| 时好时坏怎么办 | 并入上游的诊断纪律，放成参考文件 | 单独留一个诊断 skill | 第二轮精简时把它并进来，少一个常驻描述；为什么选并入而不是删，材料没写 | 迭代记录（2026-11-04）；推测（理由） |
| 红线写在哪 | 一行指针指向常驻规则文件 | 每个编排器各抄一份硬约束 | 同一组约束抄了 5 份，查出 5 组跨文件不一致 | 事故复盘（2026-10-28 一致性盘点） |
| 报错类请求谁接 | 明确说「修」才归它；只想知道原因归日志首查；「解决」类小修主对话直接改 | 报错都归它 | 全闭环太重，小修走它不划算 | 本人要求（2026-11-03） |

「依据类型」只说明这条决策是凭什么定的。对应的原始材料不随本库提供，读这张卡不需要去找它们。

## 怎么用

- 我会说：「把这个 bug 修掉」「走查发现的问题修复一下」「生产报错了，帮忙修复」「时好时坏，复现不了」。
- 输出：一份运行记录（现象、根因、改了什么、派了谁、构建和回归结论、验证状态、遗留）加状态文件；有任务单的落在任务单目录。
- 不用它：只想知道原因（交给日志首查）；没有缺陷的新需求（交给单个需求入口）；有任务单号要批量跑（交给按任务单的入口）。

## 好处

| 同一件事 | 没有它 | 有了它 | 依据 |
|---|---|---|---|
| 说「把这个 bug 修掉」能不能叫到它 | 排障簇 16 条用例改前过 11 条 | 改后 15 条；修 bug 那条第一个动作不是它，探针证实第 3 步叫到了它 | 实测，评测记录（2026-11-03 簇评测） |
| 根因没定就动手改 | 边猜边改 | 门禁卡住：一次真实运行停在「等我选修复方向」 | 实测，真实运行（2026-08，1 次） |
| 回归没过 | 无限回退 | 最多 2 轮，第 3 次交人 | 设计意图，未实测。上限加上之后没有真实运行走到过 |
| 生产报错 | 只能在开发环境里猜 | 证据、结论、回退清单、回滚脚本、「待生产部署验证」都有固定写法 | 设计意图，未实测 |

## 代价与局限

- **几乎没被用起来。** 近 400 天 1 次；2026-11-05 到 11-23 改业务代码的 10 个会话里调用 0 次，实际做法是「计划模式 → 主会话直接改 → 编译重启 → 浏览器自验 → 派审查」。同样的现象见[能力装得多用得少，瓶颈在采纳](../50-经验教训/能力装得多用得少瓶颈在采纳.md)。
- **门禁停下之后没人接。** 2026-08 两次实跑：一次停在门禁等我选修复方向，一次停在「等我手动重启后回归」；到 11-03 复查时都还挂着。
- **派的 agent 多，用量大。** 一次完整闭环要派 4～5 个子代理，和[默认不派子代理铺开](../10-协作规矩/默认不派子代理铺开.md)那条规矩有张力。
- **子代理定义改了要重开会话才生效**，见[项目级子代理什么时候加载](../40-技巧/项目级子代理什么时候加载.md)。

## 踩过的坑

1. **描述里写的能力，流程里没有。** 「线上」写在描述里，流程只会在开发环境跑；补了线上分支才对上。
2. **同一组约束抄 5 份必漂移。** 「本机能不能编译」在 5 个文件里说法不一，改成一行指针后才统一。
3. **补缺口之前先跑一次红。** 2026-11-09 照复评去补「回归基线」：派走查 agent 只做「确定走查范围」，给了任务单号时它自己就找到了任务目录下的测试清单，4/4 通过，这个缺口其实不存在。只给模块名、不给任务单号的情形没测。
4. **只看第一个动作会误判没触发。** 项目规则要求先查能力索引，所以修 bug 那条用例第一步是翻索引，第 3 步才叫到它。

## 换个项目怎么复用

可以照搬的做法：

- 编排者-执行者（orchestrator-worker）：入口只串接和守门，执行全部委派。
- 先复现再修：单请求探针优先，修前红、修后绿就是回归证据。
- 复现的安全语义：只读或只用自建数据，复现不了就停下问。
- 根因加修复方案的阻断式门禁。
- 有界回环：各环最多 2 轮，超限交人（fail-to-ask）。
- 线上分支如实降级：证据来自人、结论标推断、附回退清单、不写「已修复」。
- 时好时坏的先造一条稳定变红的回路，再列可证伪的假设。
- 状态文件可续跑；字段定义只留一份。

要按项目重写的：委派给谁（日志、定位、复现、修复、构建、审查各用什么）、探针工具、回归基线放哪、落盘目录、线上的取证方式。
