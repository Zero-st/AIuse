# dev-rebuild：改完后端代码，让它在本机生效

## 是什么

改了 Java 或配置文件后，把「看改了哪些模块 → 只编这些 → 停掉自己的服务 → 重启 → 确认真的能用」打包成一条命令。它在「代码写完」和「打开浏览器验证」之间出场。

## 为什么做它

- **一个流传很久的错误说法。** 这套遗留 Java 系统的正式发版只能在另一台构建机上做，于是项目文档里一直写着「本机不能编译、不能部署」。AI 照着这个说法，改完后端代码就标「待部署」然后停下，新功能在开发环境里验不了。实际上本机开发环境完全可以编译重启，只是没人把步骤封装起来。
- **步骤零散，每次现找。** 用哪个构建工具、哪个 JDK、离线依赖仓在哪、该编哪几个模块、服务的启动参数是什么，这些都得记住。让模型每次现找，慢，还会找错。
- **多人共用一台机器。** 旁边就跑着别人的服务，按端口或进程名去停服务有误杀的风险。

## 设计思路

1. **说明文件管判断，脚本管执行。** 模型只决定该不该跑、带什么参数、怎么读结果、下一步交给谁；所有机械步骤在脚本里。
2. **先判断「不用做」**（提前退出，early exit）。页面和静态资源是热更新的，只改了它们就直接退出，不编译也不重启。
3. **失败不扩大**（快速失败，fail-fast）。编译失败就此停下，绝不去动正在跑的服务。
4. **动手前核对身份**（进程身份校验）。停进程不看「这个端口上是谁」，而是确认那个进程确实是我这个实例。
5. **脚本自己等到出结论**（就绪检查，readiness check）。调用方拿到的是「全绿」或「未全绿 + 原因」，不需要再写轮询。
6. **能预演**（预演模式，dry-run）。带预演参数时只打印将要做的事，不产生任何副作用。

## 实现思路

组成：

- 说明文件 83 行：环境事实、何时用何时不用、参数、结果怎么判读、失败交给谁。
- 实现脚本 411 行：全部机械步骤。
- 每个工作副本一份不进版本库的本地配置（配置外置，externalized configuration）：端口、调试端口、工具路径这些会变的值。
- 配套的一条按文件路径触发的规则：改到 Java 或配置文件时自动提醒「要跑它，跑之前先看有没有别人没做完的改动」。
- 触发评测集（trigger eval）14 条：8 条正例该触发，6 条负例不该触发。

一次运行的顺序：

1. 侦测：读版本库状态，把改动文件映射到构建模块；只改了页面就退出。
2. 编译：只编变更模块和它们的上游（增量构建，incremental build）；先离线，识别出是缺依赖才联网重试一次。
3. 停：核对进程身份，先正常关闭，超时再逐级强制。
4. 起：用从原进程还原出来的启动参数重启。
5. 校验：等端口监听，再有上限地等（带超时的等待，timeout）「本次重启之后新增的日志」（按偏移量读日志，log offset）里出现启动完成的标志，最后发最多 3 次健康请求。
6. 结论：打印结果摘要和一个固定的结论词，「全绿」或「未全绿」加原因。上层的编排流程就按这个词决定往下走还是停。

调用时还会自动把两样东西摆到模型面前（上下文注入，context injection）：当前副本的实例配置，和工作副本里将被一起编进去的未提交改动清单。模型不用先跑命令去找。

| 怎么让改动生效 | 刷新编译输出目录，重启进程 | 打包再部署 | 本机服务是就地展开运行的，直接挂载编译输出目录，根本没有包被部署 | 技能说明文件 |
| 编译范围 | 按版本库改动只编变更模块，另留全量和手动指定两个兜底 | 每次全量 | 省时间（推测，材料里没写理由）；侦测不准时有兜底 | 技能说明文件；推测（理由部分） |

## 怎么用

- 我会说：「改完了，编译一下」「重启，我来验证」「走查前把服务起来」。开发编排流程走到「构建」这一步时也会自动调它。
- 不带参数就是默认流程。可选：预演、只编译不重启、全量、指定模块、带调试端口。
- 产出：一块结果摘要（编了哪些模块、是否启动完成、健康码、本次新增的异常行）和结论词。
- 不用它：只改了页面或静态资源（刷新即可）；要发测试或生产环境（那是另一条流水线）；想查报错原因（交给日志排查的 skill）。

## 代价与局限

- 托管重启后服务脱离 IDE 的调试器，要调试得带调试参数重起。
- 它编的是工作副本里**所有**未提交的改动，不只是本次任务的。
- 启动参数是从当时的活进程抄下来写进脚本的，环境变了要手工同步。
- 只管本机开发环境，发版不归它。
- 启动校验改好之后，「未全绿」的比例按计划要到 2026-11-30 才在日常使用里复测，目前只有一次真实运行的证据。

## 踩过的坑

1. **端口通了不等于应用起来了。** 最早是端口一监听就发健康请求，58 次里 52 次拿到的是失败码。
2. **旧日志冒充新结果。** 旧的校验扫整份当日日志，上一次启动留下的「启动完成」和异常都被算到这一次头上，四种不同的场景输出一模一样。
3. **并发会话的半成品。** 另一个会话刚给实体类加了一个新字段、数据库还没建对应的列，这边一重启，所有用到那个实体的页面全部报错。现在的做法是跑之前先看改动清单，撞上了先问我，不擅自回退别人的文件。
4. **同一件事两处说法打架。** 另一个 skill 里还留着「自己编译、重新部署」的旧步骤，和这里的做法矛盾。后来统一改成「委派给 dev-rebuild」。
5. **构建工具的无害报错。** 构建输出里有两条固定出现的错误和警告字样，构建其实是成功的。按「有没有 ERROR」判断会误判，要以成功标志为准。

## 换个项目怎么复用

可以照搬的做法：

- 说明文件管判断、脚本管执行；脚本输出固定的结论词，给上层流程判断用。
- 提前退出（early exit）：先判断「不用做」的情况并直接退出。
- 快速失败（fail-fast）：构建失败不碰运行中的服务。
- 进程身份校验：停进程前核对它的启动参数，不按端口或名字。
- 按偏移量读日志（log offset）：记下操作前的日志位置，只看之后新增的部分。
- 带超时的等待（timeout）：等待要有上限，超时要说清是哪一种没成。
- 预演模式（dry-run）：留一个零副作用的预演参数。
- 配置外置（externalized configuration）：会变的值放进不进版本库的本地配置，脚本里只留默认值和找不到时的提示。
- 上下文注入（context injection）：调用时把现场信息（配置、未提交改动）直接注入给模型。
- 触发评测（trigger eval）：配一组用例，正例和负例都要有。

要按项目重写的：模块映射表、构建命令和参数、启动参数、端口和日志位置、「启动完成」的标志字符串、健康检查地址。
