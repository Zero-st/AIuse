# prod-data-fix：生产数据订正，套模板出一键块

## 是什么

运维工单里，业务方常请我们直接改生产数据：换单据负责人、改某个金额或日期、改人员信息、把单据退回到某个审核节点、改错的发票关联。它把工单归到五类之一，用开发库只读取证，填好对应模板的参数区，产出一个脚本块和一份说明（诉求原文、改哪几处、风险、执行步骤、回滚），交我在生产手动执行。它在「工单进来」和「我去生产执行」之间出场。

## 为什么做它

- **每次从零手写。** 每一单都要重写「参数区 + 预览开关 + 备份 + 断言 + 回滚」，还要重新查一遍：这个值冗余存在哪几张表里。
- **先用数据定范围。** 2026-11-09 把当年的 25 条事件类工单（拆开算 26 件）分了类：改数据的有 19 件，占 73%，集中在五类：换负责人 5、改字段值 5、人员账号 4、单据退回 3、发票关联 2。导出和非改数据的不走它。我之前凭印象多选的是发票、换人、退回三类，数据显示改字段值和人员信息一点不比它们少，于是一并纳入。
- **系统自带的变更功能有坑。** 页面上「变更负责人」最终调用的存储过程，对一类单据用错了关联键：真正的成员表没改到，还可能误改编号相同的另一条记录、删光它的成员；它吞掉异常后又在过程内提交。不读过程源码看不出来。

## 设计思路

1. **模板库，不往生产装任何东西。** 我选的方向是填空式模板加编排说明，不在生产建存储过程，也不做系统内的订正页面。风险最低，又能省掉重写骨架和重查表关系这两块主要耗时。
2. **三档模式，默认只读。** 预览只读，数出每处的预计行数；彩排真改后回滚，不建备份表；执行时先备份、再改、再核验，最后提交。参数默认停在预览。
3. **行数断言加旧值条件**（防御式编程）。执行时每处实际改动的行数必须等于预览数出的行数，否则整块回滚。改动条件里带上旧值，只改当前确实是旧值的行，重复执行也不会改坏别人的数据。
4. **按业务键现查，不写死生产 ID。** 单据编号、员工编号这类业务键在块里现查出内部 ID；人员一律按员工编号定位，因为有同名的人。
5. **「这个值冗余在哪几处」沉淀成参考表。** 每类涉及的表、列、关联键记在一份表关系参考里。改字段值那类做成通用的「位置清单」引擎：每个常改字段一份预设，列出它冗余存放的所有位置；遇到没有预设的字段，先查清再补一份预设。
6. **只产出，人来执行。** 不连生产、不替我执行；开发库上只读取证。生产执行块不放进发版脚本目录，否则会被发版当成发版脚本执行掉。

## 实现思路

- 组成：
  - 说明文件 48 行；
  - 一个通用骨架，7 条硬约定写在头注释里；
  - 两类专用模板：换负责人、改字段值；
  - 一份表关系参考。
  - 拉工单复用任务单工具，后来给它加了一个按查询条件批量拉单的只读子命令，明年统计用一条命令就能重跑。
- 一次运行：拉单（正文常空，诉求在标题和附件里）→ 归类，一单多件事就拆成多个块 → 开发库只读取证（核对员工编号、表、列、XML 节点在不在）→ 复制模板只改参数区 → 落盘脚本块和说明 → 交我按「预览 → 核对 → 彩排 → 执行 → 页面复核」执行，结果回填到说明末尾。
- 开发库上有同类样本时，跑一次预览做整块编译检查。数据库 MCP 拿不到过程内的输出，验证副本里先把输出攒进变量，结束时用一个自定义错误带回来；只改副本，不改模板。

## 关键决策

| 决策点 | 选了什么 | 没选什么 | 为什么 | 依据类型 |
|---|---|---|---|---|
| 做成什么 | 填空式模板库加编排说明 | 在生产装存储过程；做系统内的订正页面 | 不往生产装对象，风险最低 | 本人要求（2026-11-09） |
| 先做哪几类 | 先用工单数据分类，按件数定五类 | 按印象选三类 | 统计显示改字段值、人员信息的频率不低于印象里的三类 | 真实运行（2026 年 25 条事件类工单统计） |
| 骨架从哪来 | 沿用我之前验证过的一键执行块，含它修过的输出缓冲溢出 | 重新设计 | 已在生产用过，坑踩过了 | 设计文档（2026-11-09） |
| 怎么防改错 | 三档模式、默认预览；行数断言；旧值条件；先备份 | 只靠人看一眼 | 套模板变快以后，审视会变少，改错生产代价高 | 设计文档（风险表） |
| 人员怎么定位 | 一律按员工编号 | 按姓名 | 有同名的人 | 技能说明文件 |
| 换负责人用不用系统的变更过程 | 不用，用自己的模板；也不建议走页面变更 | 调用现成的变更过程 | 它用错关联键、吞异常后自己提交，实证改错过数据；缺陷由我决定暂不修 | 事故复盘（2026-11-09 开发库实证）；本人要求（暂不修） |
| 账号合并 | 只出预检和预览，合并本身单独确认 | 和别的类一样一键执行 | 现成的合并过程是硬删，不可逆 | 设计文档（风险表） |
| 改字段值怎么做 | 一个通用位置引擎，加每个字段一份预设 | 每个字段一个模板 | 改字段的诉求五花八门，难的是找全冗余位置，不是写更新语句 | 迭代记录（2026-11-10）；推测（理由） |
| 生产块放哪 | 放工单目录，绝不进发版脚本目录 | 和发版脚本放一起 | 发版会把目录里的脚本当发版脚本执行 | 技能说明文件 |
| 备份表名 | 统一前缀加工单号和日期，30 个字符以内 | 随手起名 | 备份表会越积越多，统一前缀便于按季度清理 | 设计文档（风险表） |

「依据类型」只说明这条决策是凭什么定的。对应的原始材料不随本库提供，读这张卡不需要去找它们。

## 怎么用

- 我会说：「这个工单把这几个单据的负责人换成某某」「改一下这个金额和日期」「退回到某个审核节点」「这笔到账关联错了发票」。
- 输出：工单目录里一个脚本块和一份说明，执行由我来。
- 不用它：随发版走的建表、字典、种子数据（交给发版脚本的 skill）；导出类、排查类、代码问题。

## 好处

| 同一件事 | 没有它 | 有了它 | 依据 |
|---|---|---|---|
| 写一个改字段值的订正块 | 从零写骨架、重查冗余位置 | 复制模板、改参数区；开发库上预览整块编译通过，两个字段预设实跑通过 | 实测，真实运行（2026-11-10，一张进行中的工单加一张历史工单回放） |
| 换负责人 | 走页面变更，可能改错成员表 | 模板按员工编号改全冗余位置，核验语句覆盖每一处 | 设计意图，未实测。计数和 XML 表达式在开发库只读验证过；整块预览和生产执行都还没做 |
| 生产上改错了 | 手工补救 | 行数不符整块回滚；执行前自动备份，末尾有回滚语句 | 设计意图，未实测 |
| 明年再统计工单类型 | 手写查询，踩「类型要写 id」的坑 | 一条只读子命令重跑 | 设计意图，未实测 |

## 代价与局限

- **只完成了两类。** 人员账号、单据退回、发票关联三类还没有专用模板，暂时从骨架派生，各有一张工单等着试点。
- **开发库和生产不一样。** 业务单据大多不在开发库，只能验结构；开发库上通过的块到生产仍可能圈错行，靠预览和断言兜底。
- **还没在生产执行过。** 两个试点块都已产出，等我执行。
- **只改本系统。** 涉及财务系统的（财务侧的负责人、核销），说明里要写明「财务侧需要财务部门配合」，不能假装这边改完就算完。
- **备份表会堆积。** 统一前缀只是方便清理，清理本身还没人做。

## 踩过的坑

1. **工单查询按类型筛选要写类型 id。** 写中文类型名会报 400。
2. **数据库 MCP 拿不到过程内的输出。** 预览结果看不见，只好用自定义错误把攒好的输出带回来。
3. **输出缓冲默认有上限。** 超过就报错，块里一开头就要放开缓冲上限。
4. **老版本数据库的语法限制。** SQL 里只能引用标量变量，不能调本地函数、不能引用集合元素的字段。

## 换个项目怎么复用

可以照搬的做法：

- 先拿工单数据分类，按件数定模板的优先级，不凭印象。
- 三档模式：预览只读、彩排回滚、执行提交；默认停在预览（dry-run）。
- 行数断言加旧值条件，任何一处不符整块回滚；先备份再改，回滚语句写在末尾注释里。
- 按业务键现查 ID，不写死生产 ID；人员按唯一编号定位。
- 「一个值冗余在哪几处」沉淀成参考表；通用位置引擎加每字段预设。
- 产出和执行分开：agent 只产出，人在生产执行；生产块和发版脚本分目录放。
- 系统自带的变更功能先读源码再信。

要按项目重写的：五类划分、表关系参考、模板里的数据库方言和输出方式、工单工具、落盘目录。
