# to-questionnaire：拍不了板的事，写成问卷交给知道的人

## 是什么

有些决定我一个人定不了，得问懂行的人：业务口径问业务方，部署环境问运维，一个模块的历史问原来的开发。它先问我两件事：发给谁、要拿回什么。然后写一份问卷：背景一段、怎么答、按主题分组的问题（最重要的在前，每题只问一件事，下面留答案位），最后一个「还有什么我们没问到的」。对方可以异步填，也可以开会时一起过。说明文件除了描述和第 3 步里本地加的一段，是上游原文。

## 为什么做它

- **为什么装。** 2026-10-20 评估那个公开仓库时，我挑了 4 个和项目栈无关的 skill 装进项目，它是其中之一。
- **它补的是什么。** 需求分析的 skill 已经会出「需求待确认清单」，但那是绑定某个需求的，编号要回灌到需求文档里。还有一类问题不挂在某个需求上：一个方案要问外部的人，一段历史要问原来的开发。这类问题之前没有固定的写法（推测，材料里没有直接写这条动机）。

## 设计思路

上游原有的设计（不是我定的）：

1. **只追问「发送」，不追问「主题」。** 我答不了主题本身的问题，不然就不用发问卷了；但「发给谁、要拿回什么」我总能答。问卷里的问题瞄准两者之间的缺口：对方知道、而我需要的东西。
2. **两问各一轮。** 一轮问清对方的角色、专长、和我的关系，这决定问卷的语气和要带多少背景；一轮问清我要拿回哪些决定或事实，这是问卷必须覆盖的清单。
3. **为异步填写排版。** 对方可能只填一遍，所以最重要的问题放前面；每题只问一件事，不出复合题；容易被误读或随手敷衍的题，加一行「为什么问这个」。
4. **「不知道」也有用。** 写明部分作答、「我不确定」都欢迎，标出来就行，不要跳过。

本地改的：

5. **落盘按项目的文档规范。** 写到对应模块的资料目录里，后缀用规范词表里已有的「待办」类，不新造后缀。
6. **和需求分析划清边界。** 某个需求或任务单的待确认问题，不归它写，停下来指向需求分析的 skill。
7. **对方不懂技术时，套待确认清单的风格。** 不出现表、字段、SQL 这类黑话；推荐选项放第一个并标「推荐」；能勾选就不用填空；末尾放答复汇总和签字栏；用中文写。文件已存在就追加一节带日期的，不覆盖。

## 实现思路

- 组成：一份说明文件 54 行，一份来源说明（上游地址、版本、许可全文、本地改动、升级步骤）。没有脚本。只能手动运行。
- 一次运行：问发给谁 → 问要拿回什么 → 按模板写问卷，确认第 2 问列出的每一项都有题目覆盖 → 报文件路径。
- 升级方式：拉上游同一路径的文件比对，再重放本地改动（供应商化，vendoring）。

## 怎么用

- 我会敲：命令后面跟要问的事。它先问我「发给谁、要拿回什么」。
- 不用它：某个需求或任务单的待确认问题（交给需求分析，那份清单的题号要回灌）；我自己就能定的事（直接定，或者用逐轮追问的 skill 把自己的想法问清楚）。

## 踩过的坑

1. **两个 skill 抢同一个文件。** 它原来也会写需求分析那份固定文件名的待确认清单，两边写同一个文件会互相覆盖；2026-11-03 改成它不写，遇到就指过去。
2. **想新造后缀被规范拦下。** 原计划把文件改名成「问卷」后缀，查了文档规范才发现类型后缀是封闭词表，只好沿用已有的「待办」类。
3. **改一处要连带改几处。** 不写待确认清单这条，说明文件、来源说明的本地改动清单、项目能力索引的两处要一起改。

## 换个项目怎么复用

可以照搬的做法：

- 只追问「发送」：发给谁、要拿回什么，我总能答；问卷的问题瞄准缺口（上游）。
- 为异步填写排版：重要的在前，每题一件事，容易误读的加「为什么问这个」，末尾兜底题（上游）。
- 写明「不知道」也欢迎作答（上游）。
- 和已有的同类产物划清边界，固定文件名只归一个 skill。
- 给非技术读者时：无黑话、推荐选项在前、能勾选就不填空。
- 外来 skill 用供应商化（vendoring）的办法维护，做法同 [handoff 技能卡](handoff.md)。

要按项目重写的：落盘目录和后缀、和需求分析的边界、非技术读者的问卷风格模板。
