# handoff：换新会话前写一份交接文档

## 是什么

一个会话做到一半要换新会话时，让 agent 把当前会话压成一份交接文档，新会话读它就能接着干。它在「这个会话该收了」的时候出场。说明文件只有十来行，几乎全是上游原文；本地改的是触发方式、落盘位置和「不要复述哪些东西」这三处。

## 为什么做它

- **为什么装。** 评估那个公开仓库时逐个读了约 30 个 skill，工程类的大多绑定 git、代码托管平台的 issue 和某一种测试栈，和本项目对不上；最后由我挑了 4 个和项目无关的装进来，它是其中之一。
- **为什么改成能自动触发。** 上游设成只能手动敲命令。这样的 skill 描述不进模型的可选列表，我说「写个交接，我开新会话继续」时模型调不到它，只能现读说明文件照做，或者提醒我去敲命令。
- **为什么改落盘位置。** 上游写到系统临时目录，而我的规矩是临时文件一律放专用的临时目录，不用系统临时目录。

## 设计思路

上游原有的设计（不是我定的）：

1. **交接的价值是「能搬走」，不是「压缩」。** 上游作者的文档说，只有工作要「走」的时候才需要一个文件：换一个 agent 工具、换目录、交给同事、分叉出一条支线。同一工具、同一目录接着干，用内置的压缩上下文命令（/compact）就够了。
2. **只写活的部分，已写下来的按位置引用。** 规格、计划、提交、差异这些已经落盘的东西不抄进来，只给位置。文件小，定下来的细节也只有一份，不会两份各自漂移（一处一源）。
3. **附一节「建议调用的 skill」。** 告诉下个 agent 该先调哪些 skill。
4. **按下个会话的目的取舍。** 调用时可以带一句「下个会话做什么」，文档就围绕它保留理由，不平铺所有细节。
5. **写之前先脱敏。** 密钥、个人信息这类敏感内容不进文件。

本地加的：

6. **能自动触发，但只在我主动提出时。** 描述里写死「只在用户主动提出交接时用，任务进行中不要自行触发」，并划清和相邻几件事的边界。
7. **「不要复述的东西」换成本项目真有的几类：** 需求和设计文档、计划和进度账、任务单目录、记忆、版本库差异。

## 实现思路

- 组成：一份说明文件（正文保留上游原文，只在三处换成本地说法）和一份来源说明（上游地址、版本、许可全文、本地改动清单、升级步骤）。没有脚本。
- 一次运行：模型按说明写文档，存到固定的临时目录，文件名是「日期-主题-handoff」，最后报回绝对路径。我在新会话里指着这个路径说「读它，接着做」。
- 升级方式：把上游同一路径的文件拉下来和本地比对，再按来源说明里的清单重放本地改动（供应商化，vendoring）。

| 怎么防误触发 | 描述写明只在我主动提出时用，划清和「总结改动」「更新进度表」「写需求文档」的边界；评测加两条负例 | 不加约束，靠模型自己判断 | 放开以后最大的风险就是误触发：我说「总结一下」「下次再做」时它跑去写文件 | 设计文档（2026-11-20 风险表）；评测记录 |
| 描述写多长 | 去掉前缀约 190 字，在项目给自动触发 skill 定的 300 字预算内 | 保留上游的一句英文 | 仅手动时描述不进模型列表；自动触发全靠描述里的触发词 | 设计文档（2026-11-20） |
| 防升级覆盖 | 来源说明里写明「上游仍是仅手动，升级时别覆盖回去」 | 不记 | 重放升级时这一行最容易被带回去 | 设计文档（2026-11-20 风险表） |
| 改动范围 | 只改主项目这一份 | 另一个工作副本和另一个项目的副本一起改 | 控制范围，后续按需同步 | 设计文档（2026-11-20） |

## 怎么用

- 我会说：「写个交接，我开新会话继续」「把当前会话压成交接文档」。可以带一句下个会话要做什么。
- 产出：一份交接文档，含现状一句话、下一步、先读哪些（不复述）、坑、未决、建议调用的 skill；回复里给出它的绝对路径。
- 不用它：只是总结这次改了什么，直接回复；更新进度账，交给进度表 skill；写需求或设计文档，交给 prd-to-md。

## 好处

下表的「它」指本地改过的这一版。「不复述已有产物」和「建议调用的 skill」两节是上游原有的设计。

| 同一件事 | 没有它 | 有了它 | 依据 |
|---|---|---|---|
| 说「写个交接」能不能触发 | 改前模型调不到，交接那条用例命中 0 | 改后每条用例跑 2 遍，交接那条 2/2 命中 | 实测。评测记录：同一簇 12 条用例，改前 10/12，改后 12/12（2026-11-20） |
| 会不会误触发 | 无从比较 | 「总结一下这次改了哪些文件」「把今天的进展更新到进度表」两条负例改后都没误触发 | 实测。评测记录（2026-11-20） |
| 交接文档会不会把计划整段抄进来 | 模型自由发挥 | 3 份真实交接文档都有「先读这些，不在此复述」和「建议调用的 skill」两节，长 53～128 行 | 实测。真实运行（2026-11-03、11-04、11-20） |
| 交接文件放哪 | 系统临时目录，路径长、可能被清 | 固定目录，按日期和主题命名，报回绝对路径 | 设计意图，未实测 |

## 代价与局限

- **自动触发只在评测里见过。** 放开以后，统计到的 3 次都是我手动敲的命令，模型自己调用 0 次。
- **常驻上下文每轮多约 200 字描述。** 仅手动时这部分是 0。
- **和上游的定位有偏差。** 上游说同一工具、同一目录接着干就用压缩命令，交接文件是给「要搬走」的情况用的。我 3 次实际使用都是同一台机器、同一个工具、同一件事换新会话，描述里还放了「上下文太长了，交接一下」这样的触发词。为什么不用压缩命令，材料里没写。推测是想要一份能留档、能指给新会话的文件，新会话从干净的上下文开始也更省用量（读缓存的开销随上下文变大，见[用量怎么量、预算怎么写](../40-技巧/用量怎么量、预算怎么写.md)）。
- **记得「做了什么」，不一定记得「为什么」。** 上游文档点名的问题：会话里没核实过的判断（「某某还没做」「某某已完成」）被写成事实，下个 agent 会照单全收、不再核对。交接前自己读一遍，把只是猜测的降级成猜测。
- **三份副本行为不一致。** 主项目这份能自动触发，另外两份仍是仅手动。

## 踩过的坑

1. **仅手动 skill 对模型是隐形的。** 描述不进可选列表，用户用自然话提出时模型找不到它。
2. **改一行元数据要连带改三处。** 项目能力索引写着「仅手动」，技能库检查脚本会报错；项目常驻规则文件把它列在「只能手动运行」的清单里；触发评测里有一条「交接 → 不该触发」的负例要反过来改成正例。漏改任何一处，检查和评测就会互相打架。
3. **本地改动清单漏记过一条。** 「不复述的产物」换成本地对应物是在技能库分层优化时改的，来源说明的本地改动清单里一度没有这一条，升级时照清单重放就会把它丢掉。2026-11-23 写卡时拿上游逐行比对才发现，次日补进清单。

## 换个项目怎么复用

可以照搬的做法：

- 供应商化（vendoring）：外来 skill 的正文保留原文，本地改动集中、逐条记在来源说明里，升级时比对上游再重放。装之前先核对原文，见[装外部组件前核对一手来源](../10-协作规矩/装外部组件前核对一手来源.md)；另一种打补丁的做法见 [archify 技能卡](archify.md)。
- 交接只写活的部分，已落盘的东西按位置引用（上游）。
- 交接文档带「下个会话建议调用的 skill」一节（上游）。
- 调用时说清下个会话的目的，让文档按目的取舍（上游）。
- 把仅手动改成自动触发之前，先写负例，按先红后绿跑触发评测。

要按项目重写的：落盘目录和命名、「已有产物」的清单、描述里的触发词和划界。
