# 用量怎么量、预算怎么写

**做法**：

怎么量：从会话记录实测，不拿工具自己报的数当依据。Claude Code 的会话记录一个会话一个 jsonl 文件，每条回复带 `usage`。把写入缓存、读缓存、输出三项分别累加；派了子代理的，子代理的记录要一起算；只想看某一段的，按时间截取。会话中途每完成一个大步骤自查一次，超了就停下告诉我。

怎么估：预算写两项，新增量（写入缓存加输出）和轮数。

- 输出约等于要写的字节数乘 1.5（含思考）；
- 新读入约等于要读的字节数乘 0.45；
- 读缓存约等于轮数乘（起始约 5 万加新增量的一半）；
- 再乘 1.3。

系数只来自一个会话，做完用实测修正。

计划模式里定预算，先量已经花掉的。量的是整个会话，计划阶段读文件花掉的也算在内。在计划里写预算之前先量一次已花多少，预算写成「已花 X 加执行增量 Y」，或者只量执行段。

三条规律：

- 读缓存是大头：每一轮都重读整个上下文，用量约等于轮数乘上下文大小。
- 会话越长越贵：两个 50 轮的会话比一个 100 轮的便宜。一个会话只做一件事。
- 停顿超过一小时缓存过期，整个上下文要重新写入（一次约 35 万）。久停之后开新会话比接着聊便宜。

agent 自己的做法：少开轮数，能并在一条命令或一批工具调用里的就并；脚本只打摘要；不整份读大文件；给估算时写清是哪一种 token。

**为什么**：2026-11-12 我问开工提示词里的 token 预算怎么估，agent 从会话记录实测出来这些数（单位：万 token）：

| | 轮数 | 写入缓存 | 读缓存 | 输出 |
|---|---|---|---|---|
| 主会话，两天 | 164 | 255 | 5531 | 54 |
| 12 个子代理 | 981 | 607 | 25470 | 154 |

主会话平均每轮读缓存 34 万。工作流自己报的「510 万」远小于真实用量，不能当依据。

「先量已经花掉的」是同一天踩出来的。做一个图文页时，agent 在计划里写「本会话新增量 15 万」，没先量已花的；计划阶段读了十几个脚本和计划文件，执行到一半（三张图交付完）自查已是 21.9 万、14 轮，只能按止损停下。

实测环境：2026-11-12。原文没有记录实测版本。升级后先验证再用。

依据类型：使用统计（2026-11-12 从会话记录数出）；事故复盘（2026-11-12 计划里没先量已花的，执行到一半超预算止损）。

**什么时候用，什么时候不用**：

- 用：开工前给任务定 token 预算；会话中途自查用量。
- 不用：原文没有记录。
