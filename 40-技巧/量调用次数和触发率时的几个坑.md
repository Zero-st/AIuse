# 量调用次数和触发率时的几个坑

**做法**：评估自己的 skill、agent 用得多不多、触发得准不准之前，先过一遍下面几条。

触发评测：

- 用 skill-creator 自带的 `run_eval` 测触发率时，它会建一个名字带 uuid 的临时命令来检测触发。同名的正式 skill 已经装着的话，正式版会把临时命令遮蔽掉，结果全判「未触发」。正确跑法二选一：①在一个没装 skill 的隔离项目里跑；②把检测口径改成正式 skill 的名字。测量失真时不要据此改描述，原文的说法是「过拟合坏测量」。
- 只看第一个动作来判定有没有触发，会有假阴性。结果是 0/2 这种时，用探针看前 N 步再下结论。

数会话记录：

- 用正则从会话记录里取证，口径容易写错。写进计划之前，先人工抽看 2～3 条命中样本。
- 子代理报告的「0 命中」，主会话复核一遍再用。
- 数调用次数用固定的脚本，按调用去重，别临时手写扫描。

**为什么**：

- 2026-07-28 跑触发基线：用 `run_eval` 让 Opus 跑了约 84 次 `claude -p`，三个 skill 一致是 0 次触发。探针实证其中的日志排查 skill 其实能触发，0 是评测工具造成的假象。当时据此没有改描述。
- 2026-11-03～04 改 skill 描述时做簇评测，发现「首个动作」判定有假阴性，于是定下 0/2 时用探针看前 N 步。
- 2026-11-04 从会话记录取证，一条正则把正常的 `svn status` 算成了全量 diff。
- 2026-11-05 复评时，调研子代理说某个探针脚本没登记进项目的能力索引，实际索引里有两处。
- 2026-11-23 复评时，手写的扫描没去重，把审查 agent 的 8 次数成了 16 次。之后做了一键体检脚本，复评和复测先跑它。

同类的另外两次记在 [agent-craft 技能卡](../20-技能/agent-craft.md) 里：「踩过的坑」第 1 条是自带触发评测 10 条全 0；「好处」表里是用量统计没去重时记 35 次，去重后是 9 次。

实测环境：2026-07-28 至 2026-11-23。原文没有记录 skill-creator 和 Claude Code 的版本。升级后先验证再用。

依据类型：评测记录（2026-07-28 触发基线；2026-11-03～04 簇评测；2026-11-05 复评）；使用统计（2026-11-04 会话记录取证；2026-11-23 复评统计）。

**什么时候用，什么时候不用**：

- 用：统计 skill、agent 的调用次数；跑触发评测；从会话记录里取证。
- 不用：原文没有记录。
