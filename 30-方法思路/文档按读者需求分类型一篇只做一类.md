# 文档按读者需求分类型，一篇只做一类

**做法**：

先定这篇回答哪一种读者需求。按文档分类法（Diátaxis）分四种：学习、做事、查阅、理解。写不清自己属于哪一种，多半是混了两种，拆成两篇，互相链接。

落到项目里，用一张封闭的类型词表，每种类型只回答一个问题：

| 类型 | 回答什么 | 属于哪种需求 |
|---|---|---|
| 设计 | 这次改动为什么这么做、怎么做、链路怎样（向前看） | 理解 |
| 解读 | 已有的模块业务上做什么、技术上怎么实现（往回看） | 理解 |
| 溯源 | 某一列、某一个值从哪来 | 理解 |
| 分析 | 根因、排查、诊断、评估的结论 | 理解 |
| 调研 | 选型、方案对比 | 理解 |
| 报告 | 一次走查、审查、诊断的快照 | 查阅 |
| 参考 | 速查表、配置清单、字段对照，只查不读 | 查阅 |
| 待办 | 待办、测试、待开发清单 | 做事 |
| 指南 | 操作手册、实战教程 | 做事、学习 |

- **词表封闭。** 要加新类型，先改词表再用。不临时造同义词：「方案」归设计，「说明」「机制分析」归解读，「排查结论」归分析，「清单」归待办或参考。
- **文件名写成「主题-类型」**，类型只放后缀，看文件名就知道是哪种文档。主题写清「什么对象的什么事」，控制在约 30 个字以内；只用连字符分词，不用空格、下划线、括号。工具依赖的固定文件名原样用，不套这个格式。
- **一篇只做一类。** 同一篇里既有设计又有走查结果，拆成设计和报告两篇。
- **类型后缀一旦被工具拿来分流，含义就冻结。** 比如知识库按后缀把设计文档归成一类，解读和调研就绝不能用设计的后缀，否则会被归错。
- **放哪也按顺序问。** 按顺序问几个是非题，第一个答「是」的就是它的位置；顶层只放模板和规范；同一主题只开一个目录，开新目录前先看有没有现成的；再维护一份总索引，每篇一行。这是唯一位置加总索引的思路（Johnny.Decimal）。

每类文档该有哪几节：

- **设计**：大白话总览 → 背景与目标 → 关键决策与选型 → 为什么这么改、带来什么好处（优化、改造类才写）→ 逻辑模型 → 端到端链路图 → 落点清单 → 验证方式 → 已知限制和未决。
- **解读**：一句话定位，附和易混对象的区分表 → 业务视角（大白话）→ 专有名词和易混点 → 技术视角 → 常见误区 → 证据索引。业务视角怎么写，见[给新人讲一块业务要回答的九个问题](给新人讲一块业务要回答的九个问题.md)。
- **待确认清单**（给不懂技术的需求方）：一句话说清这个功能 → 按主题分组的问题，每题写背景、请确认、答复三栏 → 其他补充 → 答复汇总表和签字栏。
  - 不写技术黑话，但保留需求方必须知道的系统现状约束，这类约束往往正是要确认的原因。
  - 能从系统现状给出合理默认的，在选项里标「推荐」并放第一位，让对方认可即勾选；纯业务决策不替对方拍板。
  - 题号和需求分析文档里的待确认问题一一对应，回填后能直接回灌。
- **报告、待办、参考**：可以不要大白话一节。

跨类型的底线：

- 设计、解读、分析、指南、调研开头先讲大白话，见[技术文档先讲清是什么](../10-协作规矩/技术文档先讲清是什么.md)。
- 只引用、不复述：需求文档里已有的字段表、状态机，设计文档链过去，不再抄一份。
- 证据可追：代码写到位置，数据写到「表.列」，结论注明怎么取证的（只读查询、日志、走查截图）。
- 验证程度如实写：本机验证过不等于已经上线。
- 优化、改造类文档加「为什么这么改、带来什么好处」一节，见[优化文档写清为什么改和带来什么好处](../10-协作规矩/优化文档写清为什么改和带来什么好处.md)。

**为什么**：

2026-10-08，一个项目的资料目录里有 146 份文件，命名五花八门，讲 AI 工具和方法的元文档和业务文档混放在一起，看文件名分不出是哪种文档、还有没有效。我选的做法是先定规范，再列清单分批整改存量。规范借了文档分类法的「一篇只服务一种读者需求」、决策记录（ADR）的状态生命周期、唯一位置加总索引这几条公开做法。

存量整改在 2026-10-08 到 10-10 分三批做完：业务文档归到各自模块，元文档集中到单独的目录，顶层只剩模板和规范。之后新写的文档按这套命名和放置。

依据类型：本人要求（2026-10-08）；流程规范（2026-10-08）；迭代记录（2026-10-08 至 10-10 存量整改）。

**什么时候用，什么时候不用**：

- 用：一个项目的文档多起来（几十篇以上），或者多人、多个 agent 往同一处写。
- 可以简化：只有几篇文档的小项目，词表和放置规则可以省，「一篇只做一类」仍然适用。
- 不用：聊天回复、临时笔记、一次性的草稿。

**例子**：

- 不合格：一份「报销模块说明」，前半讲现有的审批流程，中间是这次加「超标说明」的方案，最后贴了上周的走查结果。读者不知道该从哪读，半年后也不知道哪部分还有效。
- 合格：拆成三篇，`差旅报销-解读`、`超标说明-设计`、`差旅报销走查-20261120-报告`，互相链接；每篇开头带一张文档头表，见[文档头写明状态，废弃不删、指向替代](文档头写明状态废弃不删指向替代.md)。
