# 文档头写明状态，废弃不删、指向替代

[文档按读者需求分类型，一篇只做一类](文档按读者需求分类型一篇只做一类.md)管一篇文档是哪一类、叫什么，这条管它开头写什么、过时了怎么处理。

**做法**：

标题下面紧跟一张「项｜值」小表：

```markdown
| 项 | 值 |
|---|---|
| 类型 | 设计 / 解读 / 溯源 / 分析 / 调研 / 报告 / 参考 / 待办 / 指南 |
| 状态 | draft / review / accepted / implemented / superseded（→ 新文档链接）/ deprecated |
| 模块 | 业务模块名 + 关键入口（页面地址、类、表），能精确到一处就精确到一处 |
| 关联 | 任务单号；没有就写来源，如「口述需求 2026-09-23」；上下游文档链接 |
| 最后更新 | YYYY-MM-DD |
```

状态借决策记录（ADR）的生命周期，只描述文档自身：

| 状态 | 含义 |
|---|---|
| draft | 起草中，结论可能变 |
| review | 等需求方或我确认 |
| accepted | 已拍板，可以照着执行 |
| implemented | 设计已落地；写清验证到哪一步，比如「本机已验证，生产待部署」 |
| superseded | 被新文档取代，必须附新文档链接 |
| deprecated | 已失效，没有替代 |

配套的几条：

- **废弃不删。** 改状态、指向替代者，保留当时的推理。确认要删的，先备份，并同步删掉索引里那一行。
- **报告是一次性快照。** 写完即 accepted，之后不再更新；结论变了，新写一份带日期的报告。
- **只留一份当前版本。** 文件名里不放「最新」「最终版」「v2」「副本」，旧结论靠 superseded 保留。只有快照类（报告、一次性执行的脚本）可以在文件名里加日期。
- **文档状态和任务进度分开。** 任务做到哪一步另有任务状态，不写进文档状态。
- **改名、移动、删除前先查引用，改完修引用。** 没有版本管理的目录，批量改动前先整目录备份。
- 原件附件、图片、给工具读的状态文件不用加文档头。

**为什么**：

和文档类型同一天定的（2026-10-08），目的是半年后回来看，扫一眼就知道这份还有没有效。

那个资料目录没有纳入版本管理，删了就找不回来，也没有历史可以回退。所以不靠「最终版 v3」这类副本区分新旧，而是只留一份当前版本，旧结论用 superseded 状态加链接保留下来。之后新写的文档普遍带这张表。

依据类型：本人要求（2026-10-08）；流程规范（2026-10-08）。

**什么时候用，什么时候不用**：

- 用：会被反复回看、可能被新方案取代的文档，比如设计、解读、分析、调研、指南、规范。
- 报告写完就定格，只填一次头。
- 不用：聊天回复、临时笔记。

**例子**：

「超标说明」的设计被新方案取代了：

- 不合格：复制一份「超标说明-设计-最终版v2」，旧的那份原样留着，没有任何标记。后来的人分不清该照哪份做。
- 合格：旧文档状态改成「superseded → 超标说明按职级分档-设计」，正文不动；新文档状态写 draft，关联一栏链回旧文档。
