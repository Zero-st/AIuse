# 项目文档规范只维护一份规则真源

## 什么时候用

项目的文档规则散在 README、代理指令或技能里，几个入口对同一篇文档的类别、名字或存放位置给出不同答案。

## 做法

1. **把可维护的规则归到一处。** 在一份文档里说明什么值得长期保存、有哪些文档类型、怎么命名和登记。开新文档前先查能否补充原文，过程记录沿用项目已有的留痕入口。
2. **让入口负责导航。** 仓根 README 和代理指令给出规则指针。文档索引一篇一行，写清读者在什么情况下该点进去。技能入口告诉代理什么时候读取规范。
3. **让机器检查读取同一份词表。** 检查索引漏收、死链和目录命名是否匹配。规则表坏掉或解析为空时让校验明确失败，避免检查失效后误放行。
4. **保留人工复核。** 比对入口里的转述是否长成了另一份规则，检查索引里的人数、版本等具体断言是否跟上。当前脚本只覆盖能识别的规则副本形态。

## 例子与依据

2026-09-21，一次文档盘点发现同一套规则有 3 份副本。有的规定治理文档留两篇，有的规定三篇，根目录的决策记录列表也落后于实际文件。项目随后集中维护分类和词表，让入口引用原件，并把词表解析失败纳入检查。

2026-11-24 复跑 4 项词表定向用例，覆盖读取、格式缺失时拒绝、未知位置及命名匹配，均通过。「已验证」限于历史盘点与这些机器检查，文档判断和转述漂移仍需人工复核。

依据类型为真实运行（2026-09-21，3 份规则副本冲突）和评测记录（2026-11-24，4 项定向测试）。
