# 这个库的由来和规划

本文是从当初几份建库计划改写来的转述，讲清这个库为什么是现在这个样子。计划原文带着本机路径，不随本库提供。

## 为什么建

2026-11-23，我想把日常用 AI 攒下的技能、思路、想法、技巧、经验整理成一个资料库，让不同的 agent 都能了解我的使用习惯。

当时这些东西散在四个地方：全局规则、记忆、skill、我的 Obsidian 笔记库。换一个 agent（Codex、Hermes、网页版），它就什么都不知道；我自己想翻，也没有一处能看全。

当时实数：

- Claude Code 的全局规则 46 行。
- 一个主力项目的记忆 127 条：偏好 20、项目 79、指针 28。其中通用的初筛约 24 条，和项目事实混在同一个目录里。另外几个项目的记忆，少的一两条，多的 32 条。
- skill 34 个：全局 15 个、项目 19 个，分在两个目录。
- Codex 的配置只有 24 字节，里面没有我的任何习惯。

还有一个影响设计的发现：20 条偏好里约 7 条其实是某个项目专属的。所以「通用」不能按记忆的类型自动判断，要靠一份人工过目的收录清单。

## 最初怎么规划

三轮追问之后定了 12 个决定。后来有几条被取代或改了，「现在」一列标出：

| # | 决定 | 当时选的 | 现在 |
|---|---|---|---|
| 1 | 主要读者 | agent 优先，人也能翻；纯 Markdown | 不变 |
| 2 | 和 Obsidian 笔记库的关系 | 完全独立，不引用、不建软链接 | 不变 |
| 3 | 和现行规则的关系 | 导出一份快照进库，原处的规则照常生效 | 已取代：快照不进库，只在本机留作备份；库里的规矩改成可移植的转述 |
| 4 | 首版接入 | 只接 Claude Code，结构做成通用的 | 不变 |
| 5 | 收录范围 | 只收通用的 AI 使用内容；不收业务事实、账号密码、内部地址 | 不变；后来补了两条：带单位域名的不进库，拿不准的默认不收 |
| 6 | 快照做法 | 脚本导出到库里独立的快照区，可以重跑 | 已取代：脚本和快照一起移到本机目录 |
| 7 | 目录结构 | 按内容类型分 | 不变；快照区腾出来的 10 号位置给了协作规矩 |

| 11 | 技能目录 | 脚本生成全部 skill 的清单，心得另外手写 | 改了：清单随快照留在本机；库里写技能卡，等卡写得差不多再用一页总览代替清单，总览已写（2026-11-24） |
| 12 | 版本管理 | 首版不做，样品验收后再定 | 已定：用 git 管理（2026-11-24 我认可）；agent 自己的计划目录不进仓库 |

当时的设计：

- 库里分两个区：「抄出来的」，用脚本把现行规则、通用偏好、工具经验、skill 清单抄一份；「新写的」，我说一句「记到 AiUse」，agent 就按固定模板写一条技巧、教训或想法。
- 分三阶段：先做样品（目录骨架、入口说明、几条样品、收录清单），我验收后写导出脚本，最后接入 Claude Code。
- 样品验收不过就退一步，只保留入口说明和综述两个文件，其他推倒重议。
- 用 3 道探针题验收「别的 agent 读得懂我」：用一个不加载任何个人配置的纯文本模型，只喂入口说明和综述，问它：
  1. 我让你给一个技术方案，回复里必须有什么？
  2. 一个任务能拆给 10 个子代理并行，你怎么做？
  3. 我提了一个新工具的想法，你第一步做什么？
- 不把这个库做成唯一真源、再反过来生成全局规则。当时的理由：现在的规则好用，生成脚本出错的代价高于收益。

当时的判断：这个库最可能的失败不是技术问题，而是建好了没人写，或者格式不合我用。所以先做样品，再投入脚本。

当时识别的风险：

- 手写区长期没人写，库里只剩快照；
- 快照过期，别的 agent 把旧规则当现行；
- 敏感信息被抄进来；
- 综述是归纳写的，和原规则有出入。

当时写下的「本方案自身的风险」是：同一条规则存在两份，有人手改了快照或者忘了重跑，两份就不一致。

## 后来两次改方向

**第一次，技能卡去本机化（同一天）。** 样品技能卡的「出处」「依据」写的是本机的文件名、行号、计划名、记忆名。病根在技能卡模板当初的要求上：必须写出处，写到哪份计划、哪条记忆。我的原话：「出处和依据里面的路径和文档名都没有用。我迁移到不同机器，完全找不到这些，给其他 AI agent 会带来干扰。都改写成通用规范的技术名称」。于是：

- 出处改成「依据类型」，从一张词表里选，比如实现代码、设计文档、事故复盘、评测记录；
- 做法有业内通行叫法的，附上通行叫法。第一版模型自造了 5 个听着像术语的词，后来撤了，从此拿不准的不硬标。

**第二次，全库可移植（同一天）。** 我的原话：「其中 19 条通用偏好另写成不带本机引用的可移植条目，所有保存到库中的都不要引用这些。避免迁移时造成干扰。按上面方式一样处理」。

- 当时快照区 43 个文件全部命中，共 245 行本机引用。它没法「改一改」，因为逐字照抄和不带本机引用是矛盾的。
- 于是分成两个目录，划一条界线：这个库只放可移植的内容，整个带走；快照、导出脚本、收录清单、本机约定、写条目时核对用的出处，放在库旁边一个只在本机用的目录里，不带走。快照是移过去的，没有删。
- 改写时去掉路径、文件名、行号、计划名、记忆名、项目名、单位域名、业务名词；保留日期、数字、事情的经过和我的原话。
- 这次改动自身的代价：库里的规矩从原文的副本变成了模型的转述，每一条都要我过目才算数；原处的偏好还会继续变，两边靠人工加检查脚本对齐，做不到自动同步。

**之后，分模块推进。** 剩下的条目很多，一个会话写不完，也容易乱。我的原话：「把技能，偏好，使用技巧，经验教训。等等，每个模块单独整理独立提示词，我去不同会话执行」。做法：

- 每个模块一份自成一体的提示词：背景、开工前先读、每一条怎么做、守住哪几条、边界、检查、什么时候停下来问我、完成后汇报什么。新会话只凭提示词就能做。
- 一把统一的尺子：一个检查脚本查本机引用、敏感词、文件头、库内链接、索引登记、文件名、依据类型，有一项不过就判失败。
- 断点续写：每个模块从任务清单里取「待写」的条目，写完一条改一行；中途断了，换个会话再跑同一份提示词就能接着写。
- 多会话并行不打架：每个会话只改自己那一节，用定点编辑，不整文件重写；入口说明、模板、综述，任何会话都不许改，觉得该改就提出来。

## 第三次改动：索引分层，一句话只写一处（2026-11-27，待本人审）

这一节讲 2026-11-27 对库的结构做了什么、为什么。别的机器上的 agent 拉到新版本后，先读这一节，再读入口说明的「怎么写一条」。

文中的「探针」，指让一个没有项目记忆的 agent 在空目录里按规矩查一次库，记下它读了哪些文件、花了多少。

**问题与证据。**

- 总索引有 100 行、约 2.7 万字节，每次查库都要整份读。其中协作规矩 21 行、技能卡 28 行，合起来占了近一半：规矩的一句话版本在主力机器上本来就常驻，技能卡只在改某个 skill 时才用得上。
- 每个条目有两句手写的一句话介绍，一句在文件头，一句在索引里。100 条里没有一条逐字相同。
- 全库检查报 3 项不过，其中 2 项来自不属于库内容的文件，真问题被当成了噪音。
- 接入后三天，别的项目 18 个会话里，干活前先查库的是 0 次。所以这次降的是查库的门槛，不是已经发生的浪费。

**怎么改的。**

1. 索引分层。协作规矩和技能卡的清单搬到各自目录下的 `_索引.md`，总索引只留关于我、方法、决策、技巧、教训，外加两行指针。搬的时候一个字不改。
2. 指针写明路径格式：规矩文件名就是规矩标题，技能卡文件名就是 skill 名，直接读，不用先搜。
3. 一句话只写一处。文件头的描述是唯一手写的地方，索引行照抄。合并时分两类：知识类、技能卡、关于我以原来的索引行为准；协作规矩以文件头为准。
4. 索引行末尾单独的「（已审）」不再写，状态看文件头。
5. 三个上限写进检查：总索引 18000 字节；登记在总索引里的描述 100 字；技能卡 160 行，原来是 150。

**中途被推翻的两处设想。**

- 原想「改 skill 时跳过总索引，直接读技能卡」。动手前先跑了一次探针，发现这种场合 agent 也会从总索引里挑中两条有用的教训和技巧。于是改成：什么场合都读总索引，改 skill 时另外读技能卡。
- 原想一句话一律以文件头为准。量了才知道 100 条里有 87 条是文件头那句更长，照办的话总索引会涨到贴着上限。索引行是配着标题读的写法，更短、更具体，所以知识类和技能卡以它为准。规矩是例外：它的文件头描述和常驻规则文件里那一行本来就逐字相同。

**一个没想到的意外。** 分层之后，agent 找规矩文件和技能卡时各多用了一次文件名搜索。多出来的一轮要重读整个上下文，比小索引省下的还多。把指针写成明确的路径格式后，这次搜索消掉了。

**带来什么好处。**

| 同一件事 | 改前 | 改后 |
|---|---|---|
| 查一次库要读的总索引 | 约 2.7 万字节，100 行 | 约 1.5 万字节，51 行 |
| 一句话介绍 | 两处手写，没有一条相同 | 只写文件头一处，索引行照抄 |
| 规矩的一句话 | 文件头、子索引、常驻规则文件三处，子索引那句不同 | 三处同一句 |
| 全库检查 | 3 项不过，分不清真假 | 全部通过，新加的检查都做过反向测试 |

探针里，同一道查库题读入的总索引降到原来的 55%，挑中的条目没有变差。

**代价与局限。**

- 索引从一份变成三份，登记位置多了一条规则。
- 70 个条目原来的文件头描述换成了索引行的写法，原句只在版本记录里。
- 短会话里省不了多少，长会话才明显。没人查库这个根本问题没有解决。
- 探针每种情况只跑了一次。
- 同步脚本和全库检查只在主力机器上，不随库走：检查脚本里带着那台机器上的名字清单。

**没有这两个工具的机器怎么办。** 照入口说明「怎么写一条」第 4 步，手工保持三件事：规矩和技能卡登记到所在目录的索引，其余登记到总索引；索引行的文字照抄文件头描述；登记在总索引里的描述不超过 100 字。对不上的地方，回到主力机器跑检查时会被点名，在那里改对。

依据类型：使用统计（2026-11-25 至 27 的会话记录）；评测记录（2026-11-27 五次查库探针、同步脚本 11 项反向测试）；迭代记录（2026-11-27）；本人要求（2026-11-27 逐步确认）。

## 还没做的

- 创始计划里写着「以后再说」的几项：
  - 给 Codex、Hermes 的入口配置各加一行指针；
  - 一份可以整段贴给网页版 AI 的「关于我」单文件；
  - 接入一个月后数一下手写区的条数，大约在 2026-12-23。少于 5 条，说明「靠我想起来说」这个录入方式不行，那时再考虑让 agent 在会话收尾时提议。
- 决策记录目录约 2026-12-25 复查：数一下有没有新写的，别的项目有没有读过这个目录。两样都是 0，就和我商量要不要并回 `30-方法思路/` 或 `50-经验教训/`。原来定的「不满 5 条就撤」不再用：2026-11-26 收窄收录条件以后，条数本来就少。
- 接入的后两层：约 2026-12-09 再数一次别的项目读库的次数，还接近 0 的话，试做一个按提问内容匹配条目、注入标题的钩子；反复踩的坑按「复发第 2 次」逐条升级成守卫钩子，候选是派子代理和起无头 Chrome 不加密钥环参数。
- 另一批写入里等补全的 4 条：在写它们的那台机器上把来历、怎么做、好处补全，再由我审。
- 同步脚本和全库检查只在主力机器上。别的机器上写的条目，要回到主力机器才查得出不一致；同一类不一致出到第 2 次，再考虑让这两个工具随库走。

依据类型：设计文档（2026-11-23 的四份建库计划）；本人要求（2026-11-23 建库、分模块）；本人纠正（2026-11-23 两次可移植）。
