# 能力装得多用得少，瓶颈在采纳

**做法**：

- 要改自己的 skill 库之前，先用固定的脚本数一遍实际调用了哪些、各几次，别手写扫描。量的时候容易踩的坑见 [量调用次数和触发率时的几个坑](../40-技巧/量调用次数和触发率时的几个坑.md)。
- 原文的说法：「抵制『再建一个 skill/agent 解决采纳问题』的冲动」，理由是「会加重错配」。
- 新建能力的门槛，原文写的是：「需求复现≥N 次+eval 证明有用」才建，「闲置即整合退役」。
- 找到缺口时不新建，给现有能力补一节或补一步。
- 判定缺口之前先跑一次红。原文的说法：「『文档里没写』≠『行为缺失』，缺口判定要先跑一次红再动手」。
- 别再去优化编排器的触发描述。这条的依据是下面那段推测。
- 要为一个入口放宽权限（比如远程批准提交代码、写库）之前，先看这个入口有没有被用起来。

**为什么**：同一件事前后量了好几次，结论一直没变。

- 2026-07-27，对一个项目的 Claude 能力体系做审计。体系里有四层流程文档、约 30 个具名模式、9 个 skill、4 个 agent、6 个钩子、一个知识库和一条每日自评的定时任务。可是 132 个会话里只有约 13 次 skill 调用；按任务单批量开发的编排器全程只跑过 1 次，那次收尾还带着问题；skill 调用的趋势在归零。原文的诊断是「真正瓶颈是投入产出错配」，结论是：「别再加方法论，先让存量被用起来/被证明有用/停止自我漂移」。
- 2026-07-28，行为评测：审查 agent 6/6，测试改动里植入的注入、业务常量误用、吞异常全部命中，另外多找出 3 处；日志排查 skill 5/5。原文的结论：这两个能力「该干活时干得对」，不是摆设，采纳缺口是触发和门槛的问题，不是能力的问题。
- 2026-08-05，对 16 个 skill 做评估：架构 A 级，集成度和纪律 B 级；元问题仍是「过度建设vs采纳」。
- 2026-11-03，覆盖复评找出 7 处缺口。按「先证明有用才建」的门槛，新建 0 个，全部给现有 skill 补一节或补一步。
- 2026-11-05，复评：项目 skill 有 10/18 零调用，其中包括刚新建的 2 个。
- 2026-11-09，照复评的建议先红后绿去补一个缺口，结果改之前就是绿的：派走查 agent 只做「确定走查范围」，它自己找到了任务目录下的测试清单，4/4 通过，skill 没改。同一天另一个缺口也一样：审查 agent 对写在提示词里的口述需求，改之前就是 4/4，agent 没改；真正要补的只是一个钩子的提议文案。
- 2026-11-23，统计 11-05 到 11-23 的会话：有工具调用的 67 个，改业务代码的 10 个。这 10 个里走计划模式的 7 个，用编译重启 skill 的 8 个，主会话直接用浏览器自验的 7 个，派审查 agent 的 4 个。三个编排器（需求开发、缺陷修复、按任务单批量开发）、开发 agent、测试先行、复盘、知识库重建全是 0 次。
- 2026-11-17，做了一个从手机即时通讯工具远程驱动 AI 编码会话的桥接程序，换掉 3 个月只完成 1 个任务的旧远程审批方案。同时把提交代码、写开发库从一律禁止放开成两步确认：AI 当时推荐一律禁止，本人选了放开。主程序约 1600 行，另有约 700 行自测。到 11-25，留痕里只有上线当晚的 1 个任务，两步确认实际触发 0 次。换了入口、放宽了权限，用量还是没起来。只有一周数据。

当时的判断，原文自己标了「推测，没做对照实验」：「计划模式的审批顶替了编排器的设计门禁和根因门禁；被用起来的能力都有机械触发器（路径规则、Stop hook）。所以别再去优化编排器的触发描述。」

依据类型：评测记录（2026-07-27 审计；2026-07-28 行为评测；2026-08-05、2026-11-03、2026-11-05 评估；2026-11-09 先红后绿）；使用统计（2026-07-27；2026-11-05～2026-11-23）；真实运行（2026-11-17～11-25 远程桥接程序的留痕）；推测（计划模式顶替编排器门禁那段）。

**什么时候用，什么时候不用**：

- 用：想再建一个 skill、agent 或流程，来解决「AI 没照流程走」的时候；复盘或评估自己的能力体系的时候。
- 不用：原文没有记录。

**例子**：

- 2026-11-03：找到 7 处缺口，新建 0 个，全部给现有 skill 补一节或补一步。
- 2026-11-09：以为走查 agent 不会自己找回归基线，先跑了一次，结果 4/4 通过，于是没改。
