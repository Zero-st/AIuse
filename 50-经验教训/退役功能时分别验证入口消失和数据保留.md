# 退役功能时分别验证入口消失和数据保留

## 什么时候用

功能有菜单、旧链接、API、后台任务、浏览器缓存或用户数据，需要正式退出。开工先明确外部调用者的迁移期、数据保留责任、备份的恢复方式，以及旧链接和旧接口的预期表现。

## 做法

1. **先列撤销和保留清单。** 逐项查导航、启动脚本、API、写入动作、缓存资源、扩展入口和指标。受保护原数据单独备份或记录指纹，旧文档标明历史状态并给当前入口。
2. **同时验两侧。** 从旧 URL 或已持久化的旧视图进入，看能否落到可用页。对已撤销的 API 检查约定返回及无写入、无任务启动。按用户常走路径验剩余功能，留意共享模块中的初始化和样式。
3. **用旧版本缓存试升级。** 构造实际使用过的缓存起点，确认新版本清除旧资产并保留需要的最后成功数据。停服务整页重载后核对离线表现，再恢复服务重试。
4. **复核数据和历史。** 比对受保护文件指纹、备份完整性及保留配置。报表中撤下退役指标，既有历史记录保留区间含义。

## 为什么与例子

2026-10-28 一次本地网页应用退役删除了 37 个已备份文件。接口、旧导航状态和缓存升级纳入回归。真实页面仍发现保留视图漏引用共享数据，以及启动时残留的旧弹窗，补修后复验。另比对了 1216 个受保护文件，指纹均保持一致。

依据类型为本人要求（已批准退役范围）、迭代记录（真实走查发现并修正残留）、真实运行（保留视图与停服务重载）和评测记录（历史定向 116 通过、1 项系统能力跳过，2026-11-24 复跑缓存生命周期脚本通过）。外部客户端迁移、备份实地恢复及用户接受新定位没有验收证据。文件指纹证明当时被核对的文件一致。
