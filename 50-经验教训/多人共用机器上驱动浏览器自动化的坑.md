# 多人共用机器上驱动浏览器自动化的坑

已有条目讲过的这里不重复：

- 起无头 Chrome 前查端口、连之前核对属主、按进程号结束自己的进程、`--remote-allow-origins='*'`，见规矩 [共享机上起服务前先查端口](../10-协作规矩/共享机上起服务前先查端口.md)。
- 单页应用别新开页面或刷新；共享机上按名字数出的上百个进程大多是别人的。见 [chrome-walkthrough-flow 技能卡](../20-技能/chrome-walkthrough-flow.md) 的决策表和「踩过的坑」。

**做法**：

- chrome-devtools MCP 的 `take_screenshot`，filePath 只能落在当前工作区里，放到工作区外的临时目录会被拒。省事就不传 filePath，截图内联返回。
- 非交互会话、自动模式会话里，chrome-devtools MCP 的调用（连 `list_pages`）会被权限分类器拒绝，或者挂到超时。这时浏览器走查交给我在交互会话里跑，或者自己起一个独立的无头 Chrome。
- 独立的无头 Chrome **能**连到 127.0.0.1 上的端口。最小配方：

  ```bash
  google-chrome --headless=new --disable-gpu --no-first-run --no-default-browser-check \
    --remote-allow-origins='*' --user-data-dir="<临时目录>/<任务名>/profile" \
    --remote-debugging-port=<先确认空闲的端口> about:blank
  ```

  Python 一侧 `import websocket`，用 `create_connection(url, suppress_origin=True)` 连。`--remote-allow-origins` 和 `suppress_origin` 两个都要，否则握手 403。起来之后用 CDP 的 `Page.navigate` 导航；在 `--headless=new` 下把 URL 直接写在命令行上，页面会停在新标签页。
- 无头模式下剪贴板必失败，`navigator.clipboard` 和 `execCommand('copy')` 都返回失败。复制行为验不了，别把页面上的「请手动复制」提示当回归。
- 判断常驻的调试浏览器在不在，直接看端口和进程，别看 systemd 服务的状态。
- 浏览器工具卡住时，先别怀疑 `npx -y chrome-devtools-mcp@latest` 拉起慢：已缓存时约 2～3 秒，不是卡点。

**为什么**：

2026-09-03，在非交互的自动模式会话里，chrome-devtools MCP 的调用（连 `list_pages`）被权限分类器直接拒绝。退而起独立的无头 Chrome（`google-chrome --headless=new`），`data:` 页能渲染，但请求始终没到达本机后端的日志，加 `--no-proxy-server` 也无效。当时记成：沙箱网络限制，别再花时间绕。

2026-09-24 实测推翻了后半句。用 `--dump-dom` 打本机端口上的一个单页应用，拿到了页面标题和完整 DOM（1.2MB）；随后经 CDP 驱动真实点击也成功了：按钮渲染出来，`click()` 不抛错，页面的输入框收到 450 个字符。前半句仍然成立，同一天 MCP 的 `list_pages` 直接挂到超时。原文更正时特意写了「别再照它放弃」。

同一天还发现：记录里写常驻的调试浏览器由一个 systemd 服务拉起，实测该服务是 inactive，当时跑着的是手动起的进程。

实测日期见上，原文没记 Chrome 和 chrome-devtools MCP 的版本。升级后先验证再用。

依据类型：事故复盘（2026-09-03；2026-09-24）。

**什么时候用，什么时候不用**：

- 用：在多人共用的 Linux 机器上，用 chrome-devtools MCP 或自己起的无头 Chrome 驱动浏览器。
- 不用：原文没有记录。

**例子**：

- 不合格：看到「无头 Chrome 连不到本机端口」的旧记录，就放弃无头方案。
- 合格：按上面的配方起，带上 `--remote-allow-origins='*'` 和 `suppress_origin=True`，再用 `Page.navigate` 导航。
