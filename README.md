# AiUse：我的 AI 使用资料库

这里集中放我使用 AI 的习惯、规矩、技能、技巧和教训。任何 agent 开始替我干活前，读这里就能知道我怎么用 AI、希望你怎么配合。我自己也在这里翻查和记录。

这个库是可移植的：里面的内容不引用任何一台机器上的路径、文件或文档，可以整个拷到别的机器、交给别的 agent 读。读它不需要去找库外的任何东西。

## 怎么读

1. 先读 [00-关于我/工作方式.md](00-关于我/工作方式.md)。一页，讲我和 AI 协作的主要规矩。
2. 再看 [INDEX.md](INDEX.md)，按一句话描述挑和当前任务有关的条目读，不用全读。
3. 想知道某条规矩的完整说明和来历，去 `10-协作规矩/`；想知道某个 skill 为什么这么做，去 `20-技能/`。
4. 想知道这个库为什么是现在这个样子，读 [00-关于我/这个库的由来和规划.md](00-关于我/这个库的由来和规划.md)。

## 目录

| 目录 | 放什么 |
|---|---|
| `00-关于我/` | 我怎么和 AI 协作的综述 |
| `10-协作规矩/` | 我对 AI 的固定要求，一条一个文件：要怎么做、为什么、什么时候适用 |
| `20-技能/` | 技能卡：一个 skill 为什么做、怎么设计、关键决策、怎么用、好在哪；也放工具的使用心得 |
| `30-方法思路/` | 判断原则：遇到某类情况该怎么想 |
| `35-决策记录/` | 一次被推翻、或上线后出了意外的具体取舍：比过哪些选项、为什么否掉、踩到了什么 |
| `40-技巧/` | 可以直接照做的具体操作 |
| `50-经验教训/` | 有具体事故或数字的教训 |
| `60-想法/` | 还没验证过的想法 |

## 三条必须知道的规则

**可移植。** 写进这个库的东西，都不引用只在某一台机器上才有的东西：库外的路径、文件名、行号、计划名、记忆名、项目名。带这些内容的原文备份、导出工具、本机的目录约定，一律不放在这个库里。库内文件互相引用用相对链接可以，因为它们跟着库一起走。

**这里的条目是转述。** 我的规矩最初是在日常使用里一条条定下来的，这里把其中跨项目通用的部分改写成了不依赖具体环境的说法。如果你所在的环境里另有我正在生效的规则（比如 agent 自己的规则文件和记忆），和这里不一致时以那边为准；没有的话，这里就是准绳。

**会改变 agent 行为的内容先让它生效。** 新的偏好和规矩（「以后都要这样做」）先照旧记进 agent 自己的记忆或规则文件，那样才会马上生效；跨项目通用的，再到 `10-协作规矩/` 写一条可移植的。不改变行为的技巧、教训、想法，直接写进这里。

## 怎么写一条（我说「记到 AiUse」时）

1. 判断放哪个目录。拿不准时按这个顺序对：
   - 是我对 AI 的固定要求 → `10-协作规矩/`，用下面的规矩模板
   - 讲一个 skill 的来龙去脉 → `20-技能/`，用技能卡模板
   - 讲一次被推翻、或上线后出了意外的取舍 → `35-决策记录/`，用下面的决策记录模板；只是普通选型、没出过意外的，不写
   - 有具体事故或数字 → `50-经验教训/`
   - 能直接照做 → `40-技巧/`
   - 是判断原则 → `30-方法思路/`
   - 还没验证 → `60-想法/`；验证后挪到对应目录，把 status 改成「已验证」
2. 先查 [INDEX.md](INDEX.md) 有没有讲同一件事的条目。有就改那一条，不新建。
3. 新建一个文件，文件名用中文短标题，内容按对应的模板。
4. 在 [INDEX.md](INDEX.md) 对应小节加一行：`- [标题](目录/文件名) — 一句话`。

通用模板（方法思路、技巧、经验教训、想法用它）：

```markdown
---
name: <短名，kebab-case>
description: <一句话，agent 靠它决定要不要读>
type: 方法思路 | 技巧 | 经验教训 | 想法 | 技能心得
scene: [写代码, 写文档, 排查问题, 自动化, 学习研究]
status: 已验证 | 未验证
reviewed: <本人审过的日期；没审过不写这一行>
date: <写入日期，YYYY-MM-DD>
---
**做法**：……
**为什么**：……（来自哪次经历；有数字写数字）
**什么时候用，什么时候不用**：……
**例子**：……
```

写的时候：

- 一个文件只讲一件事。
- 和已有条目部分重叠时，只写没覆盖的部分，开头用相对链接指过去；主题相关的，在文末加一行「**相关**：」，用相对链接加半句理由。
- 「为什么」写来历：哪次经历、当时的数字。没有来历的先放 `60-想法/`。
- 用我的原话或原意，不要润色成我没说过的结论。原话加引号。
- 不写账号、密码、token、内部 IP 和域名、他人姓名、业务数据。举项目里的例子时把这些去掉。
- 守住可移植：不写库外的路径、文件名、行号、计划名、记忆名、项目名。要说一条结论有什么依据，写它是哪一类依据，从下面的词表里选。
- 做法有业内通行叫法的，中文说法后面括号附上，比如快速失败（fail-fast）。拿不准有没有通行叫法的不硬标，更不要自己造一个听着像术语的词。
- 说到某个工具里才有的东西，以通用说法为主，必要时括号注明在那个工具里叫什么。公开工具的名字可以写，它们换一台机器照样成立；不写的是它们在某台机器上的安装位置。
- 讲具体工具行为的条目，写明是在哪个版本、哪天实测的，并写一句「升级后先验证再用」。命令、参数、环境变量名、配置键逐字照抄，不改写。

## 依据类型词表

规矩条目和技能卡共用。写法是 `依据类型（日期或一句限定）`，多个用分号隔开，例如「事故复盘（2026-10-22）；迭代记录（2026-10）」。

| 依据类型 | 指什么 | 通行叫法 |
|---|---|---|
| 本人要求 | 我明确提出的要求 | stated requirement |
| 本人纠正 | 我否掉了某种做法之后定下来的 | user correction |
| 事故复盘 | 出过问题之后的记录 | postmortem |
| 迭代记录 | 某次优化改了什么、结果如何 | changelog / retrospective |
| 评测记录 | 触发评测、离线回放、对照测试的结果 | eval results |
| 真实运行 | 日常使用中的运行结果统计 | production data |
| 使用统计 | 从会话记录里数出来的次数和用量 | usage telemetry |
| 实现代码 | 脚本或代码里的逻辑和注释 | source code |
| 技能说明文件 | skill 自带的说明 | skill definition |
| 设计文档 | 动手之前写的方案、提案 | design doc |
| 流程规范 | 项目的流程和方法文档 | process doc |
| 推测 | 材料里查不到，是推出来的 | inference |

依据类型只说明一条结论是凭什么定的。对应的原始材料不随本库提供，读这个库不需要去找它们。

## 协作规矩的模板

```markdown
---
name: <短名，kebab-case>
description: <一句话：要 agent 怎么做>
type: 协作规矩
scene: [写代码, 写文档, 排查问题, 自动化, 学习研究]
status: 草稿，待本人审 | 已审
date: <写入日期，YYYY-MM-DD>
---

# <规矩，一句话>

## 要怎么做
可以直接照做的几条。

## 为什么
来历：发生过什么、当时的数字、我的原话。末尾另起一行标依据类型。

## 什么时候适用，什么时候不适用

## 例子
合格的做法和不合格的做法各一个。没有合适的就不写这一节。
```

## 决策记录的模板

只收两种取舍：方案被推翻过；或者上线后出了设计时没想到的意外。只是一次普通选型、没出过意外的，不写。依据：2026-11-25 用「给条目和不给条目」对照问一个纯文本模型，普通选型的那条不给也答得出，给了反而让答案变窄；有用的只有「被否掉的方案和原因」「事后才发现的意外」两部分。

和别的目录的分工：适用于很多场合的一般判断原则，放 `30-方法思路/`；只有出过的事、没有比过选项的，放 `50-经验教训/`；关于某个 skill 本身怎么设计的决定，留在技能卡的「关键决策」表里。

```markdown
---
name: <短名，kebab-case>
description: <一句话：在什么问题上选了什么，后来怎样>
type: 决策记录
scene: [写代码, 写文档, 排查问题, 自动化, 学习研究]
status: 已验证 | 未验证
reviewed: <本人审过的日期；没审过不写这一行>
date: <写入日期，YYYY-MM-DD>
---

# <在什么问题上，选了什么>

**问题**：要解决什么，一句话。
**约束**：当时的硬条件，用通用说法。
**考虑过的选项**：表格四列：选项、好处、代价、结论。被否的选项也写，写清为什么否。
**踩过的坑和意外**：事后才发现、设计时没想到的事。换项目时最该看的一节。
**选了什么，为什么**：谁拍的板分开写。本人定的写「本人」；AI 提议、本人采纳的，写清楚。
**代价和已知限制**：……
**什么时候该重新考虑**：哪些条件变了要回头看。
**后来怎样（原项目的经过）**：上线了没有、有没有被推翻、实际运行的结果。没有记录的写「没有记录」。开头写一句：这是原项目的经过，换项目时只取约束和坑，不要当成读者自己的现状。
依据类型：……
**相关**：……
```

status 记的是选中的方案有没有真实跑过：跑过才写「已验证」，只跑通了一部分的在「后来怎样」里写清范围；只在本机或测试里跑过、或者一次都没用过，写「未验证」。

## 技能卡

讲清一个 skill 的来龙去脉时用 [20-技能/_技能卡模板.md](20-技能/_技能卡模板.md)。它比通用模板多了设计思路、实现思路、关键决策、换个项目怎么复用这几节，并要求每条决策标明依据类型、做法附上通行叫法。样例是 [20-技能/dev-rebuild.md](20-技能/dev-rebuild.md)。
