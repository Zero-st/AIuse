# 反向代理后面的应用切全站 https：分三步上线，不把协议识别只押在容器配置上

**问题**：一个系统 http 和 https 都能打开，但用 https 进来走统一认证登录，回来时常被带回 http。要做到全站只走 https，登录全程不降级。

**约束**：

- 加密在最前面的网关终止，应用容器收到的是明文，所以它认为每个请求都是 http。统一认证的回调地址、代码里的绝对跳转，都跟着容器认为的协议拼。
- 统一认证有一份回调地址白名单，由单位的认证管理方维护，当时只登记了 http。登录时带的回调地址和验票时应用拼出的地址必须一致，不一致就整批登录失败。
- 网关和容器的配置归运维，应用方看不到，从外网也验证不了。
- 单位外的用户经 WebVPN 访问，它会改写页面里的绝对链接。登录页里那个写死 http 的回调地址，当初就是为了让单位外也能登录。

**考虑过的选项**（核心是让验票那一侧也拼出 https）：

| 选项 | 好处 | 代价 | 结论 |
|---|---|---|---|
| A 容器按代理头识别协议：网关透传协议头（通常是 X-Forwarded-Proto），容器据此判断请求是不是 https（Tomcat 里是 RemoteIpValve） | 业内标准做法；配一次全站生效，回调地址和所有绝对跳转自动变成 https，不用逐处改代码 | 全靠运维配置。来源地址不在容器的内部代理名单里、头没透传、多级代理把头叠成两个值，任何一条都会让它不声不响地失效；应用方从外面验不了 | 设计时的主路线 |
| B 登录页的回调地址也改成跟随容器协议动态拼 | 不用写死地址 | 2026-06 试过：单位内能登、单位外登不进。单位内直连是明文，拼出 http，和白名单一致；单位外经加密代理进来，拼出 https，和白名单对不上 | 否掉，回到写死 |
| C 代码里按地址强制 https：登记在名单里的地址，登录和验票都强制拼 https | 不依赖运维；登录和验票走同一个拼接函数，两边一定一致 | 只对登记的地址生效，要逐个加；是绕开容器的补丁 | 设计时没有列；A 被证明没生效后补上，作为兜底 |

**踩过的坑和意外**：

- 两个外部前提都是说做好了，实际没做：运维「已配好」的容器识别实际没生效；10-27 被告知「已加」的白名单，移动端这个地址其实也没登记。
- 验票后的相对跳转，被生产容器补成了 http 开头的绝对地址。本机容器不这么做，复现不了。改成手写 302 状态码和相对的 Location 头，绕开容器。
- 设计时把「容器把相对跳转拼成绝对地址」评成「低」可能性，缓解写的是「配好容器识别后会自动变成 https」，也押在 A 上；A 一失效，两个问题叠在了一起。

**选了什么，为什么**：

2026-10-27 定的上线顺序。方案是 AI 写的，本人采纳：

1. 外部先做：认证管理方在白名单里加 https 地址，http 的先保留，回滚要靠它；运维配好协议头和容器识别；http 到 https 的 301 跳转最后再开。
2. 应用改和协议无关的代码：写死 `http://` 的跳转改成相对路径，导航菜单的绝对地址改成相对地址。这一步在 http 下照样能用，可以先上线。
3. 白名单和容器识别都确认生效之后，才把登录页写死的回调地址改成 https，单独提交一次，便于单独回滚。

设计文档写明的理由：

- 第 3 步提前，或者容器识别没生效，就会出现登录时带 https、验票时拼出 http，全员登录失败。顺序反了代价最大，所以这一步放最后，并且能单独回滚。
- 第 2 步和协议无关，先上不增加风险，还能减少站内降级到 http 的入口。
- 回滚必须成对：回调地址改回 http 时，要同时撤掉 301；运维撤掉容器识别时，要同时把回调地址改回 http。

本人的部分：10-27 转告，白名单已经加了，运维也已经配好，据此做了第 3 步并提交。这两件事我方都没有核实，所以设计给第 3 步定了上线门禁：在单位内网用 curl 看回调地址是不是 https，而且每条入口链路（单位内直连、经 WebVPN、有没有人直连容器端口）都要验。

**代价和已知限制**：

- 最关键的前提（容器识别协议）在应用方控制之外，只能靠门禁实测确认。
- 过渡期 http 的白名单不能删。
- 容器识别生效以后，https 下新建的会话 cookie 可能带 Secure 标记。301 没开之前，从 https 页跳到 http 页会丢登录状态（推测，没实测）。

**什么时候该重新考虑**：

- 应用自己终止加密、不在反向代理后面时，A 和 C 都用不着。
- 运维能给出一个应用方看得到的验证结果（比如内网能直接看到回调地址是 https），C 的名单就不用再扩。
- 换域名、新增入口链路（比如新的移动端入口）时，重走一遍门禁。

**后来怎样（原项目的经过）**：

这是原项目的经过，换项目时只取约束和坑，不要当成读者自己的现状。

- 2026-10-27：第 2 步本机验证通过，跳转都变成了相对路径；第 2、3 步分两次提交。
- 2026-11-02：生产截图里，一个只允许 https 的移动端内嵌网页拦下了 http 的回调地址。这说明生产容器仍把请求当 http，容器识别没生效。当天补了 C，只登记移动端的回调地址。本人反馈：上线后移动端回跳已是 https；认证管理方随后补登了 https 白名单，之后验票成功。
- 同一天又发现相对跳转被补成 http（见「踩过的坑和意外」第 2 条），改成手写 302。这次修复在生产上的结果没有记录。
- PC 端：第 3 步已提交，PC 的回调地址没有登记进 C 的名单；PC 那两处相对跳转在生产上很可能同样被补成 http（推测：同一个容器）。到 2026-11-25，PC 统一认证在生产上是否正常、容器识别后来有没有生效，材料里都没有记录。
- status 写「已验证」，范围只到移动端回跳变成 https、验票成功。
